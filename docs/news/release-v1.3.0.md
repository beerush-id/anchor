# AIR Stack v1.3.0 — File Routing, Static Generation & Realtime Sync

**v1.3.0** — [GitHub](https://github.com/beerush-id/airstack) | [View Changes (v1.2.25...v1.3.0)](https://github.com/beerush-id/airstack/compare/v1.2.25...v1.3.0)

**AIR Stack v1.3.0** is the biggest release since v1.0. It brings file-based routing with built-in MDX support, automatic static site generation on a new unified, framework-agnostic SSR core, and IRPC `Durable` — realtime state synchronization over streams. Alongside these headline features, the router gains typed route metadata and manifests, `Link` accepts route objects directly, the `Head` component becomes a full SEO toolkit, and the reactivity core hardens against prototype pollution.

## File-Based Routing & MDX

Routing in AIR Stack has always been programmatic — you built a route tree in TypeScript. Starting with this release, you can let the filesystem define your URLs instead. The new `airPages()` plugin watches a `src/pages` directory and turns each folder into a route, generating the boilerplate `route.ts` files for you — no registries, no magic strings.

```typescript
// vite.config.ts
import { airPages } from '@anchorlib/vite-ssr';

export default defineConfig({
  plugins: [airPages()],
});
```

The convention is intentionally small: a `page.tsx` or `page.mdx` file is the page itself, a `layout.tsx` wraps its children, and `[segment]` folders become dynamic routes.

Two more conventions are handy: `*.page.tsx` / `*.page.mdx` files create pages without needing a folder of their own (`docs/v1.page.mdx` → `/docs/v1`), and a `[...rest]` folder becomes a catch-all route — perfect for a custom 404 page.

```
src/pages/
├── page.tsx                 →  /
├── layout.tsx               →  root layout
├── about/
│   └── page.tsx             →  /about
├── blogs/
│   ├── page.tsx             →  /blogs
│   └── [slug]/
│       └── page.tsx         →  /blogs/:slug
└── docs/
    └── getting-started/
        └── page.mdx         →  /docs/getting-started
```

The plugin scaffolds starter content into newly created empty files, so dropping a blank `page.tsx` into a folder gives you a working page on first save. Hand-written `route.ts` files are never touched.

### MDX Pages

Markdown files become first-class pages with zero extra configuration. Frontmatter flows straight into the document: `title` and `description` render as the page title and meta description, and any additional keys are carried through as route metadata.

```mdx
---
title: Getting Started with AIR Stack
description: Build your first universal app in five minutes.
category: guide
---

# Getting Started

Write content in Markdown, drop in components when you need them.
```

An MDX page is not just a static document — it renders through the exact same route pipeline as a TSX page. Guards and providers apply, and the route's reactive state is available directly in the markup via `$state`, so content can react to live data without leaving Markdown.

```mdx
---
title: Profile
---

import { Snippet } from '@anchorlib/react';

# Welcome back, {$state.data.user.name}

Your balance is **<Snippet>{() => $state.data.balance}</Snippet>**.

<button onClick={() => $state.count++}>Like</button>
```

`$state.data` comes from the route's provider chain, and `<Snippet>` keeps the updates fine-grained — the text node updates, the page doesn't re-render.

### Route Manifests for Navigation

For sidebars, breadcrumbs, and sitemap-style navigation, the plugin also generates a route manifest — an `@airstack/manifest` package created under `.airstack/manifest` and resolved automatically from `node_modules`. It lists every content route with its canonical path and route object, and each folder gets its own subpath entry — so a docs sidebar is a direct import from `@airstack/manifest/docs`, no filtering or hand-maintained URL lists required.

```tsx
import docsRoutes from '@airstack/manifest/docs'; // generated by airPages

export function DocsSidebar() {
  return (
    <nav>
      {docsRoutes.map(({ path, route }) => (
        <Link key={path} to={route}>
          {route.metadata.label ?? path}
        </Link>
      ))}
    </nav>
  );
}
```

## Static Site Generation & Caching

Static generation is opt-in — and it happens automatically during your build. Mark a route as `static` and the server build pre-renders it to HTML. Requests are then served straight from disk (or a pluggable cache adapter) with proper `Cache-Control` headers, plus optional freshness-based invalidation via `maxAge`.

```typescript
import { createRouter } from '@anchorlib/react';

const router = createRouter();

// Pre-render one route, serve statically for an hour
const docs = rootRoute.route('/docs', { static: { maxAge: 3600 } });
```

Per-route `static` covers only that route. To pre-render the entire site, set it once on the router instead:

```typescript
// Every route is static
const router = createRouter({ static: true });
```

At runtime, requests to static routes skip re-rendering entirely and return the pre-generated HTML. The caching layer supports both disk storage out of the box and custom adapters (e.g. KV) via a small `StaticAdapter` interface.

### Truly Static Output (Zero JavaScript)

For content that should be genuinely static — no JavaScript and no hydration script shipped to the client — enable `noscript` in the plugin. The build strips every script from the output and marks the document as dehydrated, so browsers receive pure HTML, Astro-style, while you keep the full AIR Stack authoring experience.

```typescript
import { airPages } from '@anchorlib/vite-ssr';

export default defineConfig({
  plugins: [airPages({ noscript: true })],
});
```

## A Unified, Framework-Agnostic SSR Core

The React and Solid SSR stacks were previously separate implementations with a lot of duplicated logic. v1.3.0 consolidates them into a single new package, `@anchorlib/ssr`, which both frameworks now share. The result is one SSR core with unified configuration — and the same guarantees everywhere.

`createApp` is the new entry point: it takes your render view, optional IRPC HTTP router, and optional WebSocket router, and returns a complete worker — HTTP RPC, SSR, static assets, and realtime upgrades handled in one place.

::: code-group

```typescript [worker.ts (React)]
import { createApp } from '@anchorlib/react/ssr';
import { renderView } from './renderer.js';

export default createApp(renderView, {
  httpRouter, // optional: IRPC HTTP router
  wsRouter,   // optional: WebSocket router
  cache: {
    assets: 'public, max-age=31536000, immutable',
    pages: { public: true, maxAge: 86400 },
  },
});
```

```typescript [worker.ts (SolidJS)]
import { createApp } from '@anchorlib/solid/ssr';
import { renderView } from './renderer.js';

export default createApp(renderView, {
  httpRouter, // optional: IRPC HTTP router
  wsRouter,   // optional: WebSocket router
  cache: {
    assets: 'public, max-age=31536000, immutable',
    pages: { public: true, maxAge: 86400 },
  },
});
```

:::

The worker's asset resolver is cross-runtime by default — it serves static files correctly on Bun, Node.js, Deno, and Cloudflare Pages (via the `ASSETS` binding) with accurate MIME types, no configuration required. Cookie handling is unified through the same context system, so `cookies()` behaves identically in a server handler and inside a component.

## IRPC `Durable` — Realtime State Sync

The headline feature of this release. `Durable` brings the reactive state engine to realtime, distributed state: a single reactive state container that synchronizes across every connected client using a publish-subscribe model over NDJSON streams.

Create a durable state wherever it lives, connect clients to it, and mutate it like any other AIR Stack state — each change replays to every subscriber except the one who made it. No manual WebSocket message protocols, no fetch loops, no event plumbing.

```typescript
import { durable } from '@irpclib/irpc';

// Server side — the source of truth
const lobby = durable({ players: [] as string[], status: 'waiting' });

// Client side — sync into the same state
const { data } = await durable.from(bridge, durable.key('lobby'));

// Any connected client can mutate; everyone else updates automatically
data.players.push('alice');
```

`durable.get(id)` retrieves a remote durable state through a registered adapter (for example, a Cloudflare Durable Object binding), while `durable.key()` and `durable.uuid()` provide stable, namespaced identifiers. A companion `keepAlive` option for RPC declarations keeps long-lived connections healthy. WebSocket cleanup was also hardened across the transport layer.

## Router: Metadata, Manifests & Typed Links

Beyond file routing, the router itself gained the primitives that make it work.

**Route metadata.** Every route now carries a typed, mergeable metadata object via `route.meta()`. `airPages` scaffolds a `global.d.ts` for you — extend the global `AirRouteMeta` interface to declare your own keys, and they're fully typed on every route. File-routed MDX pages receive theirs automatically from frontmatter.

```typescript
// global.d.ts — scaffolded by airPages, add your own keys
/// <reference types="@anchorlib/vite-ssr/ambient" />

interface AirRouteMeta {
  name?: string;
  label?: string;
  icon?: string; // your custom key
}

// page.tsx
blogsDynamicRoute.meta({ label: 'Blog', icon: 'newspaper' });
```

**Links to route objects.** `<Link to={routeObject}>` is now the primary navigation form. Pass a route instead of a page component and get fully typed `params` and `query` props — no more string URLs to drift.

::: code-group

```tsx [React]
import { Link } from '@anchorlib/react';
import { blogsDynamicRoute } from './pages/blogs/[slug]/route.js';

<Link to={blogsDynamicRoute} params={{ slug: 'hello-world' }}>
  Read more
</Link>
```

```tsx [SolidJS]
import { Link } from '@anchorlib/solid';
import { blogsDynamicRoute } from './pages/blogs/[slug]/route.js';

<Link to={blogsDynamicRoute} params={{ slug: 'hello-world' }}>
  Read more
</Link>
```

:::

Routes also support query parameters declared directly in their path (`/search?q=`), with matching and context handling updated accordingly.

## SEO & Document Head

The `Head` component is now a complete SEO toolkit. Give it a single `meta` object and it renders the title, description, canonical URL, robots directives, Open Graph and Twitter cards, hreflang alternates, and any custom meta tags — with sensible fallbacks between OG and Twitter values.

::: code-group

```tsx [React]
import { Head } from '@anchorlib/react';

<Head
  meta={{
    title: 'AIR Stack — Universal Full-Stack TypeScript',
    description: 'State, RPC, routing, and SSR in one reactive architecture.',
    canonical: 'https://airlib.dev',
    og: { type: 'website', image: '/og.png' },
    twitter: { card: 'summary_large_image' },
    jsonLd: {
      '@context': 'https://schema.org',
      '@type': 'WebSite',
      name: 'AIR Stack',
    },
  }}
/>
```

```tsx [SolidJS]
import { Head } from '@anchorlib/solid';

<Head
  meta={{
    title: 'AIR Stack — Universal Full-Stack TypeScript',
    description: 'State, RPC, routing, and SSR in one reactive architecture.',
    canonical: 'https://airlib.dev',
    og: { type: 'website', image: '/og.png' },
    twitter: { card: 'summary_large_image' },
    jsonLd: {
      '@context': 'https://schema.org',
      '@type': 'WebSite',
      name: 'AIR Stack',
    },
  }}
/>
```

:::

Structured data is a first-class citizen: the new `JsonLd` component renders `application/ld+json` script tags for rich search results, and `HeadLink` gained full `hrefLang` support for international language alternates. The same API ships in both React and Solid, and everything is SSR-safe.

## Responsive Images

The `airImage` plugin and `<Image>` component matured with finer per-import control. Import an image with `?asset` and pass per-import settings through standard import attributes — `sizes`, `format`, `quality` — and every `AirImage` object includes a `default` variant used as the fallback when no responsive size fits.

::: code-group

```tsx [React]
import { Image } from '@anchorlib/react';
import hero from './assets/hero.jpg?asset' with { sizes: '350' };

<Image from={hero} alt="Hero" />
```

```tsx [SolidJS]
import { Image } from '@anchorlib/solid';
import hero from './assets/hero.jpg?asset' with { sizes: '350' };

<Image from={hero} alt="Hero" />
```

:::

## Reactivity: Security & New Primitives

**Prototype pollution protection.** Reactive state is now safe by default against prototype pollution attacks. The `secureWrite` mode — enabled out of the box — blocks poisoned keys like `__proto__` from being assigned, merged, or parsed into state. It's fully transparent to legitimate code and can be disabled with `anchor.configure({ secureWrite: false })` if your data genuinely requires such keys.

```tsx
import { anchor } from '@anchorlib/react';

const state = anchor({ name: 'air' });

// JSON from an untrusted source — safe by default
anchor.parse('{"name": "air", "__proto__": {"polluted": true}}');
```

**New reactivity primitives.** Beyond security, the core adds a few new building blocks:

- `derived.as(factory, ...args)` — derive a value from a factory function.
- **Own-key tracking** — observers can now react when keys are added to or removed from a state object.
- **Recursive linking** — nested reactive state stays automatically connected to its parent.

For large datasets, the new `SuperList` provides a fixed-size reactive list built for virtualization — with built-in sorting, ordering, visibility filtering, and selection tracking.

::: code-group

```tsx [React]
import { superList } from '@anchorlib/react';

const list = superList<User>(users, {
  size: 1000,
  orderBy: ['name', 'asc'],
});

list.add(moreUsers);
list.toggle(3); // reactive selection set
```

```tsx [SolidJS]
import { superList } from '@anchorlib/solid';

const list = superList<User>(users, {
  size: 1000,
  orderBy: ['name', 'asc'],
});

list.add(moreUsers);
list.toggle(3); // reactive selection set
```

:::

The new `@anchorlib/core/utils` subpath export makes utilities like `sleep`, `debounce`, and type guards importable without pulling in the whole core.

## Upgrade Notes

- **Dependencies**: core packages moved from `peerDependencies` back to `dependencies` to simplify installation; React and related type dependencies were bumped to v19.2.
- **SSR**: `@anchorlib/react/ssr` and `@anchorlib/solid/ssr` now re-export the unified `@anchorlib/ssr` core — existing `createWorker`-based setups keep working, while `createApp` is the recommended entry point going forward.
- **Images**: `AirImage` objects now include a `default` variant, and the `?asset` query works as an alternative import form that accepts per-import settings through standard import attributes (`with { sizes }`).

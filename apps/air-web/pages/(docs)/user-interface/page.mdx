# User Interface

In the **AirLib**, the User Interface is built from **autonomous, self-governing components** — each one carries its own **state**, its own **behavior**, and its own **responsibility**. The parent doesn't control it; it **coordinates** with it.

This follows the web platform's natural model:
- A native **`<input>`** element **manages its own value** — you don't need JavaScript to make it work. When the user types, it updates itself.
- A `<select>` element **manages its own selection state** without parent intervention.
- A `<form>` element **collects its children's values** on submit without controlling each input individually.

The same principle applies to every component you build with the **AirLib**. JavaScript handles logic. **Elements handle presentation.** Neither dictates the other.

To keep your application **fast** and **maintainable** while building these autonomous units, we categorize UI elements by the level of power they need:

## Static UI

- **Reactivity:** None (Never changes)
- **Data Flow:** Static (Hardcoded attributes)

Static UI is just standard markup (`<h1>`, `<p>`, `<div>`). It renders once, has no state or behavior, and never updates. It belongs inline wherever you need it.

:::code-group[Static HTML elements]
```tsx [React] executable
const StaticUI = () => (
  <div className="header flex flex-col gap-4">
    <h3>Static UI</h3>
    <details open className="bg-primary/10 rounded-xl p-4">
      <summary className="cursor-pointer">Native HTML Element</summary>
      <p>Static UI is just standard markup. It renders once, has no state or behavior, and never updates. It belongs inline wherever you need it.</p>
    </details>
  </div>
);
```
```tsx [SolidJS]
const StaticUI = () => (
  <div class="header flex flex-col gap-4">
    <h3>Static UI</h3>
    <details open class="bg-primary/10 rounded-xl p-4">
      <summary class="cursor-pointer">Native HTML Element</summary>
      <p>Static UI is just standard markup. It renders once, has no state or behavior, and never updates. It belongs inline wherever you need it.</p>
    </details>
  </div>
);
```
:::

## Reactive UI

- **Reactivity:** Reactive (Updates when data changes)
- **Data Flow:** Read-Only (One-Way)

A Reactive UI is a piece of UI that presents reactive data without owning it (e.g., a simple `Label`). It reads data from a source (a `prop`, a global `store`, or a `context`) and updates itself when that data changes, but it never modifies the data or maintains its own internal state.

:::code-group[Reactive template]
```tsx [React] executable
const ReactiveLabel = template(({ text }) => (
  <p className="text-lg text-center font-bold">Current: {text}</p>
));
```
```tsx [SolidJS]
const ReactiveLabel = (props) => (
  <p class="text-lg text-center font-bold">Current: {props.text}</p>
);
```
:::

:::code-group[One-way data binding]
```tsx [React] executable
// Shared state, lives outside the component.
const counter = mutable({ count: 0 });
const increment = () => counter.count++;

const ReactiveUI = () => (
  <div className="flex flex-col gap-2 items-center">
    <ReactiveLabel text={$use(counter, 'count')} />
    <button onClick={increment}>Local Increment</button>
  </div>
);
```
```tsx [SolidJS]
// Shared state, lives outside the component.
const counter = mutable({ count: 0 });
const increment = () => counter.count++;

const ReactiveUI = () => (
  <div className="flex flex-col gap-2 items-center">
    <ReactiveLabel text={counter.count} />
    <button onClick={increment}>Local Increment</button>
  </div>
);
```
:::

## Component

- **Reactivity:** Reactive (Updates itself)
- **Data Flow:** Read & Write (Two-Way or Autonomous)

A Component is a fully autonomous, self-governing unit. It has its own **state** (e.g., `loading`, `selected`), its own **behavior** (formatting, validating), and triggers its own **side-effects** (fetching, syncing).

A Component can use two-way binding (`Bindable`) to automatically sync state with a shared source without requiring manual event callbacks.

:::code-group

```tsx [React]
import { $bind } from '@airlib/react';

// Connects the prop to the parent's state. Writes propagate automatically.
<Toggle value={$bind(settings, 'notifications')} />
```

```tsx [SolidJS]
import { $bind } from '@airlib/solid';

// Connects the prop to the parent's state. Writes propagate automatically.
<Toggle value={$bind(settings, 'notifications')} />
```

:::

:::interactive[Component Demo]
```tsx
import { setup, mutable, template, $bind, type Bindable } from '@airlib/react';

// Shared state
const settings = mutable({ notifications: true });

// Autonomous component with two-way binding support
const Toggle = setup<{ label: string; value?: Bindable<boolean> }>((props) => {
  const toggle = () => {
    props.value = !props.value;
  };

  return () => (
    <button className={props.value ? 'text-blue-500' : ''} onClick={toggle}>
      {props.label}: {props.value ? 'Enabled' : 'Disabled'}
    </button>
  );
});

// Reactive UI to present reactive data without owning state
const ToggleDemo = template(() => (
  <div className="flex flex-col items-center gap-3 p-4">
    <Toggle label="Notifications" value={$bind(settings, 'notifications')} />
    <p className="text-sm text-zinc-500">
      Parent state: <strong>{settings.notifications ? 'Enabled' : 'Disabled'}</strong>
    </p>
  </div>
));
```

<ToggleDemo />
:::

:::tip[What we learn]
We just learned how to build a stable, autonomous component that supports two-way binding (`Bindable`), and how to connect it in a presentation using `$bind`. As we can see in the console, the component setup runs once on initialization and remains stable while updates propagate without re-executing the setup function.
:::

## The Problem: Mixed Concerns

To see how this plays out in practice, let's look at how a Component differs from a standard Reactive UI. In a strictly one-way data flow model, a parent often ends up micromanaging its children:

:::code-group

```tsx [React]
import { useState } from 'react';

function NavButton({ label, isActive, onClick }: {
  label: string;
  isActive: boolean;
  onClick: () => void;
}) {
  return (
    <button className={isActive ? 'active' : ''} onClick={onClick}>
      {label}
    </button>
  );
}

function Nav() {
  const [active, setActive] = useState('home');

  return (
    <nav>
      <NavButton label="Home" 
        isActive={active === 'home'} 
        onClick={() => setActive('home')} />
      <NavButton label="About" 
        isActive={active === 'about'} 
        onClick={() => setActive('about')} />
      <NavButton label="Contact" 
        isActive={active === 'contact'} 
        onClick={() => setActive('contact')} />
    </nav>
  );
}
```

```tsx [SolidJS]
import { createSignal } from 'solid-js';

function NavButton(props: {
  label: string;
  isActive: boolean;
  onClick: () => void;
}) {
  return (
    <button classList={{ active: props.isActive }} onClick={props.onClick}>
      {props.label}
    </button>
  );
}

function Nav() {
  const [active, setActive] = createSignal('home');

  return (
    <nav>
      <NavButton label="Home" 
        isActive={active() === 'home'} 
        onClick={() => setActive('home')} />
      <NavButton label="About" 
        isActive={active() === 'about'} 
        onClick={() => setActive('about')} />
      <NavButton label="Contact" 
        isActive={active() === 'contact'} 
        onClick={() => setActive('contact')} />
    </nav>
  );
}
```

:::

This is one-way data flow — data flows down as props, events flow up as callbacks. For displaying static data, this is the right approach. However, in this interactive context, the `Nav` component ends up doing two jobs: tracking the current navigation **and** managing every button's active state.

:::caution[Why this is not ideal]
The `NavButton` can't determine if it's active on its own — the parent must compute `isActive` for each one. The `NavButton` can't activate itself — the parent must provide an `onClick` for each one. The parent is managing concerns that belong to the child, and this mixed concern grows with every button added.
:::

## The Solution: Autonomous Components

Compare with the same component using two-way binding:

:::interactive[Autonomous Components Demo]
```tsx [NavButton.tsx] /props.value = props.name/ /value?: Bindable/ /props.value === props.name/
import { setup, mutable, derived, $bind, type Bindable } from '@airlib/react';

const NavButton = setup<{ name: string; value?: Bindable<string>; onClick?: () => void }>((props) => {
  const select = () => {
    props.value = props.name;
    props.onClick?.();
  };

  // Tracker that only flips when the comparison is actually changed.
  const isActive = derived(() => props.value === props.name);

  return () => (
    <button
      className={isActive.value ? 'text-blue-500' : ''}
      onClick={select}
    >
      {props.name}
    </button>
  );
});
```
```tsx [Nav.tsx] /value={$bind/
const Nav = setup(() => {
  const state = mutable({ active: 'Home' });

  return () => (
    <nav className="flex gap-6 justify-center text-lg">
      <NavButton name="Home" value={$bind(state, 'active')} />
      <NavButton name="About" value={$bind(state, 'active')} />
      <NavButton name="Contact" value={$bind(state, 'active')} />
    </nav>
  );
});
```

<Nav />
:::

:::tip[What we learn]
We just learned how autonomous components decouple state management from side effects:
- Each `NavButton` is autonomous. It determines its own active state by tracking `props.value === props.name` with `derived()`, so it only flips when the comparison result actually changes. It activates itself by writing to `props.value`. The `Nav` component's only job is tracking the current navigation — it binds the state and lets each button handle itself.
- `value` is a **state contract**. When a `NavButton` writes to `props.value`, the binding propagates the change to `state.active` in the parent — reactively. Any component reading `state.active` sees the update automatically. There is no need for an event listener to track the change.
- `onClick` is an **event** — its purpose is for side effects. It allows external code to run side effects — logging, analytics, closing a menu — when the button is clicked. It is never meant to control the component's behavior or state. The state is handled through the binding; the event is for everything else.
:::

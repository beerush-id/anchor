# Overview

**Zero-Boilerplate, AI-Native Reactive Application Stack**

At its core, every web application exists to do three fundamental things: manage **state**, communicate with **backend logic**, and present a reactive **user interface**.

:::details[The modern web development dilemma]
Yet to achieve these three simple goals today, developers are traditionally forced to stitch together a dozen disparate tools:

- A UI framework — **React**, **Solid**, **Vue**, **Svelte**.
- A state library — **Zustand**, **Redux**, **MobX**, **Pinia**.
- An API framework — **tRPC**, **Express**, **Hono**, **Elysia**.
- A caching layer — **React Query**, **SWR**, **Apollo**.
- A streaming transport — **Socket.io**, **ws**, **Ably**.
- A form library — **React Hook Form**, **Formik**.
- A validation library — **Zod**, **Yup**, **Joi**.
- A runtime — **Node.js**, **Bun**, **Deno**.
- A deployment target — **Vercel**, **Cloudflare**, **AWS**.

Each layer introduces its own mental model, its own lifecycle, and its own failure modes. And even then, you often end up sacrificing **developer experience** just to keep the **user experience (UX)** intact, or sacrificing maintainability to preserve performance.
:::

When basic application architecture requires navigating multiple libraries and bespoke glue code, the stack gets in the way of building the product.

:::tip[What if:]
**Building an application is just writing functions and calling them?**
:::

## Anchor: Reactive State Engine

Every application is fundamentally driven by state. Whether you are managing local UI interactions, streaming server data, or coordinating backend workflows, state is the single source of truth that powers your entire system.

:::details[The problem with fragmented state solutions]
To manage state today, you typically pick a UI framework and layer several specialized tools on top:

- **React** — huge ecosystem, but you battle hook cascades, stale closures, and component re-renders.
- **Solid**, **Vue**, or **Svelte** — fine-grained reactivity without the re-render battles, but they each invent their own reactive primitives.

Whichever you pick, state is still locked inside client code, and you still need to:

- Wire a separate **server state** library — **React Query**, **SWR**, or **Apollo** — to fetch and cache data.
- Wire a separate **global state** library — **Zustand**, **Redux**, **Pinia**, or **MobX** — to hold data outside components.
- Wire a separate **form state** library — **React Hook Form**, **Formik**, or **VeeValidate** — to manage inputs and validation.
- Write bridging logic and effects to keep all these fragmented state libraries in sync.
- Wrap your application in a nested tree of **Context** providers or **Stores** just to share state across components.
- Trace through multiple stores, caching layers, and subscription chains to debug why the UI is out of sync with the data.
:::

When state lives across so many disconnected tools, keeping your application in sync becomes an endless wiring exercise.

:::tip[What if:]
**One reactive state engine handles them all?**
:::

### Fine-Grained Reactivity

Reactivity in Anchor operates at the individual property level rather than across whole components or coarse state stores. When a property mutates, only the exact listeners and DOM nodes subscribed to that property update—from server-side streaming to client rendering.

:::code-group

```tsx [React]
import { setup, Snippet } from '@airlib/react';

export const MetricsCard = setup(() => {
  const metrics = watchMetrics.once();

  return (
    <div className="card">
      {/* Isolates the read so only this fragment re-renders on mutation */}
      <Snippet data={metrics.data}>
        {({ cpu }) => <span>CPU: {cpu}%</span>}
      </Snippet>
    </div>
  );
});
```

```tsx [SolidJS]
import { setup } from '@airlib/solid';

export const MetricsCard = setup(() => {
  const metrics = watchMetrics.once();

  return (
    <div class="card">
      {/* Natively updates only this text node */}
      <span>CPU: {metrics.data?.cpu}%</span>
    </div>
  );
});
```

```ts [Server Code]
stream((state) => {
  state.data = { cpu: 45 };

  setInterval(() => {
    // Transmits only this single property mutation over the wire
    state.data.cpu = Math.floor(Math.random() * 100);
  }, 1000);
});
```

## IRPC: Reactive Network Abstraction

Connecting user interfaces to backend logic is central to full-stack development. Whether executing asynchronous queries or subscribing to real-time event streams, network communication should feel as direct and strongly typed as calling local functions.

:::details[The friction of traditional network layers]
To use server data in the UI today, you typically pick a transport and routing library:

- **Express** — define routes, handlers, middleware, no type inference across the boundary.
- **Hono** — define routes, handlers, RPC mode still needs a separate caching layer.
- **Elysia** — end-to-end types, but still needs a separate caching and streaming layer.
- **tRPC** — define procedures and routers, still wire **React Query** for caching.
- **GraphQL** — write schemas, resolvers, run code generation for every change.
- **gRPC** — write protobuf definitions, generate client stubs, handle browser incompatibility.

Whichever you pick, you still need to:

- Wire a **caching** layer — **React Query**, **SWR**, **Apollo Client** — and manually track cache keys.
- Set up **streaming** — **Socket.io**, **ws**, **Ably**, **Pusher** — with its own connection lifecycle.
- Manage **loading**, **error**, and **success** states across every component.
- Configure **retry** and **deduplication** logic per query.
- Handle **serialization** and **error formatting** between server and client.
- Write repetitive boilerplate for every new endpoint — route, handler, validation, fetch wrapper, loading state.
- Hunt through controllers and fetch strings every time you rename a route.
- Keep server and client **types in sync** manually — or run **code generation** on every change.
:::

When network communication requires so much manual plumbing, APIs become brittle and disconnected from application state.

:::tip[What if:]
**Using server data is just writing a function and calling it?**
:::

### Async Function

An async remote procedure starts with a shared contract declaring the input and return types:

```ts [src/api.ts]
type PriceFn = (ticker: string) => Promise<number>;
const getPrice = irpc.declare<PriceFn>('getPrice', {
  seed: () => 0,
});
```

On the server, you attach the database logic or business execution:

```ts [src/server.ts]
irpc.construct(getPrice, async (ticker) => {
  return db.prices.find(ticker);
});
```

Any client or backend service calls it directly as a typed Promise:

```ts [src/client.ts]
const price = await getPrice('AAPL');
```

### Streaming

Streaming follows the exact same pattern. You declare a streaming contract with real-time state:

```ts [src/function.ts]
type WatchPriceFn = (symbol: string) => RemoteState<Stock>;

// Declare your streaming API.
export const watchPrice = demoRpc.declare<WatchPriceFn>('watchPrice', {
  seed: (symbol) => ({ symbol, price: 0 }),
});
```

The server opens a stream session and pushes mutations as events occur:

```ts [src/constructor.ts]
// Bind real-time streaming logic.
demoRpc.construct(watchPrice, (symbol: string) => stream((state, resolve) => {
  state.data = { symbol, price: 150 };
  let ticks = 0;

  const interval = setInterval(() => {
    if (++ticks >= 25) {
      clearInterval(interval);
      return resolve(); // Closes the stream session.
    }

    if (state.data) {
      const change = (Math.random() * 2 - 1) * 0.5;
      state.data.price = Number((state.data.price + change).toFixed(2));
    }
  }, 500);

  return () => clearInterval(interval);
}));
```

Consuming live streams in your application is fully reactive. The client automatically manages connection lifecycles, background heartbeats, and state synchronization across the UI:

## Router: Reactive Routing Engine

Routing is more than matching URL paths—it coordinates page access, data loading, and layout composition across the entire user journey.

:::details[The limits of URL-only routers]
Whether you use **React Router**, **Next.js**, **TanStack Router**, or **Solid Router**, traditional routers treat routing purely as static URL matching. Once a page loads, you still have to:

- Write **imperative redirects** inside component effects to kick the user out if their session expires.
- Manually trigger **data revalidation** when global state changes, or force a hard page refresh.
- Build nested trees of **Error Boundaries** and **Suspense components** just to catch loading and failure states.
- Coordinate **loading spinners** manually for every async transition across your component tree.
- Wire up separate **subscription tracking** just to keep the route's data in sync with live state.
- Scatter **guard logic** across middlewares, loaders, and component render functions.
:::

When routing is disconnected from your reactive state graph, keeping page data and authorization synchronized becomes an endless manual chore.

**The route reacts to the state, not just the URL?**

### Reactive Guards & Data Providers

When routes need authorization or asynchronous data, you chain `.guard()` and `.provide()` directly onto the route definition. Guards and providers re-evaluate automatically when their reactive dependencies change:

:::code-group{group="framework"}

```tsx [React] name="react" {3,4,8}
export const userRoute = usersRoute.route('/:user_id')
  .guard(() => {
    if (!auth.isAuthenticated) {
      throw redirect(loginRoute);
    }
  })
  .provide('profile', async ({ params }) => {
    return await getUser(params.user_id);
  })
  .render(({ state }) => (
    <div className="profile-view">
      <Show when={() => state.status === 'pending'}>
        <span>Loading...</span>
      </Show>
      <Show when={() => state.status === 'success' && state.data.profile}>
        {({ name, email }) => (
          <>
            <h1>{name}</h1>
            <span>{email}</span>
          </>
        )}
      </Show>
    </div>
  ));
```

## Browser: Reactive DOM Primitives

Rich user interactions often require listening to global browser events—keyboard hotkeys, mouse pointer movements, scroll positions, or clipboard selections.

:::details[The friction of manual DOM event listeners]
Handling global browser events in component trees typically forces you to write repetitive lifecycle plumbing:

- Attach imperative `addEventListener` calls inside `useEffect` or `onMount` hooks.
- Manually manage cleanup functions with `removeEventListener` to prevent memory leaks.
- Wrap event access in `typeof window !== 'undefined'` checks to avoid breaking Server-Side Rendering (SSR).
- Write custom debounce and throttle logic to avoid layout thrashing.
- Manually synchronize raw DOM events into local component state.
:::

When browser interactions require so much manual lifecycle coordination, building responsive gestures and shortcuts becomes verbose and prone to memory leaks.

:::tip[What if:]
**Handling browser events is just writing `if`?**
:::

## Server-Side Rendering

Most real-world applications need to balance public pages that demand instant load times and search indexing with rich, authenticated dashboards that require dynamic interactivity.

:::details[The friction of modern meta-framework SSR]
Yet with modern meta-frameworks, bridging server rendering and client state fractures your architecture:

- Sprinkle **`'use client'`** and **`'use server'`** directives everywhere, fracturing your codebase across **arbitrary execution boundaries**.
- Lose access to **reactive hooks** and state on the server because traditional server components are strictly static.
- Manually parse request cookies, track mutations during render, and manually reconstruct `Set-Cookie` headers.
- Configure complex server adapters and runtime-specific shims for edge deployments.
:::

When server rendering forces you to split your application across two incompatible component paradigms, full-stack development becomes fragmented and difficult to maintain.

:::tip[What if:]
**The server just isolates the request and runs the exact same code?**
:::

});

## Workflows: Promise-like Execution Pipelines

Complex multi-step processes—like AI generation pipelines, checkout sequences, and background tasks—require coordinating asynchronous operations, conditional branches, and error recovery.

:::details[The fragility of ad-hoc async pipelines]
Writing multi-step asynchronous logic with plain functions quickly devolves into hard-to-maintain boilerplate:

- Write deeply nested `try/catch` blocks across every intermediate stage.
- Manually pass mutable state objects from one async function to the next.
- Hand-roll complex `switch` or `if/else` branching that obscures the core business logic.
- Re-implement retry policies, timeout handlers, and error fallbacks for each flow.
:::

When multi-step execution is buried under defensive error handling and imperative branching, orchestrating complex logic becomes fragile and difficult to test.

:::tip[What if:]
**Multi-step asynchronous logic is just a declarative, Promise-like pipeline?**
:::

You define multi-step pipelines with typed inputs, declarative branching, and centralized error recovery:

:::code-group{group="framework"}

```ts [React] name="react" executable
type ChatInput = {
  prompt: string;
  model: 'gpt-4' | 'claude-3';
};

const chatWorkflow = plan<ChatInput>()
  .then(
    async (input) => {
      // Step 1: Preprocessing & Context Enrichment
      await sleep(350);
      return { ...input, system: 'You are a helpful assistant.' };
    },
    { name: 'Enriching prompt context...' }
  )
  .switch(
    'model',
    {
      'gpt-4': (resolve) =>
        resolve(
          async (input) => {
            await sleep(450);
            return { text: `[GPT-4] Responding to: "${input.prompt}"` };
          },
          { name: 'Generating GPT-4 response...' }
        ),
      'claude-3': (resolve) =>
        resolve(
          async (input) => {
            await sleep(450);
            return { text: `[Claude-3] Reasoning on: "${input.prompt}"` };
          },
          { name: 'Generating Claude-3 response...' }
        ),
    },
    { name: 'Routing to AI model...' }
  )
  .catch((error) => {
    return { text: 'An error occurred.', error: true };
  });
```

## Multi-Runtime Deployment

Every application eventually needs to be deployed somewhere—whether on a dedicated Node.js or Bun server, inside a container, on Deno Deploy, or across Cloudflare Workers edge.

:::details[The vendor lock-in of runtime-specific adapters]
In traditional meta-frameworks, deploying across different runtimes requires fragmented tooling and platform lock-in:

- Install and configure separate adapter packages (`adapter-node`, `adapter-cloudflare`, `adapter-bun`, etc.).
- Rewrite streaming or WebSocket code because runtime adapter APIs differ.
- Lock your codebase into proprietary runtime APIs that break local development.
- Re-architect state and session storage whenever switching between Node.js and edge workers.
:::

When deployment requires separate adapter packages and runtime-specific shims, choosing where to host your app becomes a major technical liability.

:::tip[What if:]
**The build output is a universal Web Standard that runs natively on any runtime?**
:::

AirLib compiles to standard Web APIs (`Request`, `Response`, `fetch`, `WebSocket`). You run the exact same `dist/server/worker.js` artifact across every major runtime without adapters:

:::code-group[Universal Runtime Deployment]

```js [Bun]
import worker from './dist/server/worker.js';

Bun.serve({
  port: process.env.PORT || 3000,
  fetch: (req) => worker.fetch(req),
});
```

```js [Node.js]
import { serve } from '@hono/node-server';
import worker from './dist/server/worker.js';

serve({
  fetch: worker.fetch,
  port: process.env.PORT || 3000,
});
```

```js [Deno]
import worker from './dist/server/worker.js';

Deno.serve({
  port: Number(Deno.env.get('PORT')) || 3000,
}, (req) => worker.fetch(req));
```

```js [Cloudflare]
import worker from './dist/server/worker.js';

export default {
  fetch: (req, env) => worker.fetch(req, env),
};
```

:::

:::tip[Zero-Adapter Architecture]
No adapter packages, no proprietary runtime shims. The exact same build artifact serves SSR pages, static assets, IRPC procedures, and real-time WebSockets natively across **Bun**, **Node.js**, **Deno**, and **Cloudflare Workers**.

|---|---|---|

# Getting Started with AirLib

AirLib is a universal full-stack TypeScript framework: state, routing, remote functions, and server rendering in one reactive system. The core is framework-agnostic — the same logic runs in React or SolidJS, and only the view-layer import differs.

## **Application Structure**

Here is the structure the guide builds. It's the same shape whether you start from a template or wire it manually — each section below creates or explains one piece of it:

```
my-air-app/
├── index.html             The HTML shell — the server injects the head and the page here
├── vite.config.ts         The `airPages()` plugin
├── package.json
└── src/
    ├── router.ts          The router instance — every route hangs off it
    ├── app.tsx            The app entry — used by the client and the worker
    ├── client.tsx         Hydrates the app in the browser
    ├── worker.ts          The server entry — SSR and static assets
    └── pages/
        ├── route.ts       Generated per folder — exports `rootRoute`, `indexRoute`
        ├── layout.tsx     The root layout — the frame every page renders inside
        ├── page.tsx       The landing page
        ├── products/      The product listing and detail pages
        ├── docs/          The documentation page (MDX)
        ├── dashboard/     The admin area — guarded and data-fed
        ├── function.ts    IRPC declarations
        └── constructor.ts IRPC implementations
```

## **Layouts**

Layout is the structure of your app. It wraps the pages that render inside it — the page is the content, the layout is the frame around it.

### **The Root Layout**

The root layout is the main structure of your app. It holds the UI that is visible on every route and gives the location where the page content renders. Create `src/pages/layout.tsx`:

:::code-group

```tsx [React]
import { page } from '@airlib/react';
import { rootRoute } from './route.js';

export default page(rootRoute).render(({ children }) => (
  <>
    <header>My AirLib App</header>
    <main>{children}</main>
    <footer>© 2026 AirLib</footer>
  </>
));
```

```tsx [SolidJS]
import { page } from '@airlib/solid';
import { rootRoute } from './route.js';

export default page(rootRoute).render(({ children }) => (
  <>
    <header>My AirLib App</header>
    <main>{children}</main>
    <footer>© 2026 AirLib</footer>
  </>
));
```

:::

:::tip[What we learn]
The layout renders once and stays mounted — `{children}` is where the matched page renders, so navigation swaps only the page inside the frame, not the frame itself.
:::

### **Nested Layouts**

Sometimes a nested route also needs its own structure — a section with its own header or sidebar. In that case, give the route its own layout. Create `src/pages/products/layout.tsx`, and it wraps every page under `/products`, inside the root layout:

:::code-group

```tsx [React]
import { page } from '@airlib/react';
import { productsRoute } from './route.js';

export default page(productsRoute).render(({ children }) => (
  <div>
    <aside>Categories</aside>
    <main>{children}</main>
  </div>
));
```

```tsx [SolidJS]
import { page } from '@airlib/solid';
import { productsRoute } from './route.js';

export default page(productsRoute).render(({ children }) => (
  <div>
    <aside>Categories</aside>
    <main>{children}</main>
  </div>
));
```

:::

## **Pages**

Page is the content of a route — what the visitor sees at that URL. The layout is the frame; the page is what renders inside it.

### **The Root Index Page**

`/` is the home page. Create `src/pages/page.tsx` with a title and description — they show in the browser tab and search results:

:::code-group

```tsx [React]
import { Head, page } from '@airlib/react';
import { indexRoute } from './route.js';

export default page(indexRoute).render(() => (
  <>
    <Head meta={{ title: 'Home | AirLib', description: 'Welcome to my AirLib application' }} />
    <h1>Welcome Home</h1>
  </>
));
```

```tsx [SolidJS]
import { Head, page } from '@airlib/solid';
import { indexRoute } from './route.js';

export default page(indexRoute).render(() => (
  <>
    <Head meta={{ title: 'Home | AirLib', description: 'Welcome to my AirLib application' }} />
    <h1>Welcome Home</h1>
  </>
));
```

:::

:::tip[What we learn]
`<Head>` doesn't render in the page — it injects the title, the meta description, and the social tags into the document head, and it works the same during SSR.
:::

### **Nested Index Pages**

A folder with a layout also gets an index page — `src/pages/products/page.tsx` renders at `/products`, inside the products layout:

:::code-group

```tsx [React]
import { page } from '@airlib/react';
import { productsIndexRoute } from './route.js';

export default page(productsIndexRoute).render(() => <h1>Products</h1>);
```

```tsx [SolidJS]
import { page } from '@airlib/solid';
import { productsIndexRoute } from './route.js';

export default page(productsIndexRoute).render(() => <h1>Products</h1>);
```

:::

A folder with a page but no layout is its own route — `src/pages/checkout/page.tsx` renders at `/checkout`. The page is the route itself:



### **Markdown Pages**

Sometimes a page is a static document — a docs page, an FAQ, a policy. In that case, use MDX instead of JSX. Create a `page.mdx`; the `title` and `description` at the top of the file are what the browser tab and search results show:

```mdx
---
title: FAQ
description: Frequently asked questions about the store
---

# FAQ

Welcome back, {$state.data.user.name}!
```

A Markdown page still runs through the same route pipeline as a TSX page — route state works in the markup, and components work inside the prose.

:::tip[What we learn]
`$state` is the route's live reactive state, available right in the markup — when the data changes, the page updates.
:::

### **Dynamic & Catch-all Pages**

A folder in square brackets is a dynamic segment — `src/pages/products/[id]/page.tsx` renders at `/products/:id`, and the segment is available as `state.params.id`:

:::code-group

```tsx [React]
import { page } from '@airlib/react';
import { productsDynamicRoute } from './route.js';

export default page(productsDynamicRoute).render(({ state }) => (
  <h1>{state.params.id}</h1>
));
```

```tsx [SolidJS]
import { page } from '@airlib/solid';
import { productsDynamicRoute } from './route.js';

export default page(productsDynamicRoute).render(({ state }) => (
  <h1>{state.params.id}</h1>
));
```

:::

A `[...rest]` folder is a catch-all — the rare route whose URL you can't know upfront, because the path itself is undeterministic: a file browser, a wiki, an import path. `src/pages/[...rest]/page.tsx` matches any path under it, and the segments arrive in `state.params['*']`:

:::code-group

```tsx [React]
import { page } from '@airlib/react';
import { DynamicRoute } from './route.js';

export default page(DynamicRoute).render(({ state }) => (
  <h1>{state.params['*'].join(' / ')}</h1>
));
```

```tsx [SolidJS]
import { page } from '@airlib/solid';
import { DynamicRoute } from './route.js';

export default page(DynamicRoute).render(({ state }) => (
  <h1>{state.params['*'].join(' / ')}</h1>
));
```

:::

:::tip[What we learn]
A catch-all isn't for missing pages — it's for paths whose shape you can't predict, so the route can't declare named segments. Every remaining segment lands in `state.params['*']` as an array, and the page interprets the path itself.
:::

## **Guards & Providers**

Not every page is for every visitor, and most pages need data before they render. Both belong on the route, not in the page: a guard blocks the route, a provider loads its data — the page mounts only after its guards pass and its data is ready. Attach them in the folder's `route.ts`, so every route below the folder inherits the same check and data.

### **Guards**

A section that only some visitors may see — an admin panel, a private dashboard. Put the guard on the section's route; throw a redirect when the visitor doesn't qualify, and navigation halts before any page under it mounts:

:::code-group

```ts [React]
// src/pages/dashboard/route.ts
import { redirect } from '@airlib/react';
import rootRoute from '../route.js';
import { loginRoute } from '../login/route.js';

export const dashboardRoute = rootRoute.route('/dashboard').guard(async () => {
  if (!(await isLoggedIn())) throw redirect(loginRoute);
});

export default dashboardRoute;
```

```ts [SolidJS]
// src/pages/dashboard/route.ts
import { redirect } from '@airlib/solid';
import rootRoute from '../route.js';
import { loginRoute } from '../login/route.js';

export const dashboardRoute = rootRoute.route('/dashboard').guard(async () => {
  if (!(await isLoggedIn())) throw redirect(loginRoute);
});

export default dashboardRoute;
```

:::

:::tip[What we learn]
The guard lives on the route, not on the page — the visitor never sees the page, not even a flash. A guard on a folder's route protects every page under that folder, so one check secures a whole section.
:::

### **Providers**

A route that needs server data to render — a dashboard that shows sales. Put the provider on the route; it fetches before the page mounts, and the page reads the result typed:

:::code-group

```ts [React]
// src/pages/dashboard/route.ts
import { redirect } from '@airlib/react';
import rootRoute from '../route.js';
import { loginRoute } from '../login/route.js';

export const dashboardRoute = rootRoute
  .route('/dashboard')
  .guard(async () => {
    if (!(await isLoggedIn())) throw redirect(loginRoute);
  })
  .provide('stats', async () => {
    const res = await fetch('/api/dashboard/stats');
    return res.json();
  });

export default dashboardRoute;
```

```ts [SolidJS]
// src/pages/dashboard/route.ts
import { redirect } from '@airlib/solid';
import rootRoute from '../route.js';
import { loginRoute } from '../login/route.js';

export const dashboardRoute = rootRoute
  .route('/dashboard')
  .guard(async () => {
    if (!(await isLoggedIn())) throw redirect(loginRoute);
  })
  .provide('stats', async () => {
    const res = await fetch('/api/dashboard/stats');
    return res.json();
  });

export default dashboardRoute;
```

:::

:::code-group

```tsx [React]
// src/pages/dashboard/page.tsx
import { page, Show } from '@airlib/react';
import { dashboardRoute } from './route.js';

export default page(dashboardRoute).render(({ state }) => (
  <Show when={() => state.data.stats}>
    {({ totalSales, orders }) => (
      <div>
        <h1>{totalSales} in sales</h1>
        <p>{orders} orders</p>
      </div>
    )}
  </Show>
));
```

```tsx [SolidJS]
// src/pages/dashboard/page.tsx
import { page, Show } from '@airlib/solid';
import { dashboardRoute } from './route.js';

export default page(dashboardRoute).render(({ state }) => (
  <Show when={state.data.stats}>
    {(stats) => (
      <div>
        <h1>{stats.totalSales} in sales</h1>
        <p>{stats.orders} orders</p>
      </div>
    )}
  </Show>
));
```

:::

:::tip[What we learn]
An async provider makes navigation wait for its data — the user stays on the current page until it resolves (on the initial load, that's the browser's native loading indicator). `state.data` holds this route's providers only; child pages and layouts read the merged tree — every provider up the chain — via `context.data`.
:::

### **Provider Feedback**

Navigation waits while providers resolve. Show that it's moving — render a progress bar from the router's own progress, `router.state.progress` over `router.state.steps`:

```tsx
<Snippet>
  {() => (
    <div
      class="progress"
      style={{ width: `${(router.state.progress / router.state.steps) * 100}%` }}
    />
  )}
</Snippet>
```

### **Progressive Data Loading**

A route that needs several independent pieces of data — a dashboard with sales, orders, and alerts from sources of different speeds — doesn't have to wait for the slowest. IRPC streams push each piece as it becomes ready, and the page renders each as it lands:

```typescript
// src/pages/function.ts
import type { RemoteState } from '@irpclib/irpc';
import { irpc } from '../api.js';

export type DashboardData = {
  sales?: SalesSummary;
  orders?: Order[];
  alerts?: Alert[];
};

export const loadDashboard = irpc.declare<() => RemoteState<DashboardData>>(
  'dashboard.load',
  { seed: () => ({}), keepAlive: true }
);
```

```typescript
// src/pages/constructor.ts
import { stream } from '@irpclib/irpc';
import { irpc } from '../api.js';
import { loadDashboard } from './function.js';

irpc.construct(loadDashboard, () =>
  stream((state) => {
    fetchSales().then((sales) => {
      state.data.sales = sales;
    });
    fetchOrders().then((orders) => {
      state.data.orders = orders;
    });
    fetchAlerts().then((alerts) => {
      state.data.alerts = alerts;
    });
  })
);
```

```tsx
// src/pages/dashboard/page.tsx
import { page, Show } from '@airlib/react';
import { dashboardRoute } from './route.js';
import { loadDashboard } from './function.js';

export default page(dashboardRoute).render(() => {
  const dashboard = loadDashboard.once();

  return (
    <div>
      <Show when={() => dashboard.data.sales}>{(sales) => <SalesSummary sales={sales} />}</Show>
      <Show when={() => dashboard.data.orders}>{(orders) => <OrdersTable orders={orders} />}</Show>
      <Show when={() => dashboard.data.alerts}>{(alerts) => <AlertsFeed alerts={alerts} />}</Show>
    </div>
  );
});
```

## **Building Navigation**

You need a menu of your pages — and you don't want to maintain it by hand. Import the generated route manifest: every content page is in it, so adding a page adds it to the menu automatically:

```tsx
import routes from '@airlib-cache/manifest'; // generated by airPages
import { Link } from '@airlib/react';

export function Nav() {
  return (
    <nav>
      {routes.filter((r) => r.path !== '/').map(({ path, route }) => (
        <Link key={path} to={route}>
          {route.metadata.label ?? path}
        </Link>
      ))}
    </nav>
  );
}
```

A section sidebar is the same manifest scoped to a folder — `import docsRoutes from '@airlib-cache/manifest/docs'`. To show a friendly name instead of the path, set a label on the route; the keys are typed through `AirRouteMeta` in the `global.d.ts` that `airPages` scaffolds:

```ts
// global.d.ts
/// <reference types="@airlib/vite/ambient" />

interface AirRouteMeta {
  name?: string;
  label?: string;
}
```

## **Remote Functions**

Your page needs code that runs on the server — and you want it called, typed, and synchronized as if it were local. IRPC is that bridge: declare the contract once, implement it on the server, call it from the page. Realtime is one of its features — a function that streams its state instead of returning once — and that's what this example uses.

Install the network packages, declare the contract, implement it, and subscribe:

:::code-group

```bash [React]
npm install @irpclib/irpc @irpclib/http @irpclib/ws
```

```bash [SolidJS]
npm install @irpclib/irpc @irpclib/http @irpclib/ws
```

:::

Create the transport — the bridge between the app and the server:

```typescript
// src/api.ts
import { HTTPTransport } from '@irpclib/http';
import { createPackage } from '@irpclib/irpc';
import { WebSocketTransport } from '@irpclib/ws';

export const irpc = createPackage({ name: 'irpc', version: '1.0.0' });
export const httpTransport = new HTTPTransport({ endpoint: `/api/${irpc.href}` });
export const wsTransport = new WebSocketTransport({ url: `/ws/${irpc.href}` });

// Switch to `wsTransport` for near-zero latency.
irpc.use(httpTransport);
```

Declare the function contract — typed once, available on both sides:

```typescript
// src/pages/function.ts
import type { RemoteState } from '@irpclib/irpc';
import { irpc } from '../api.js';

export type Visitor = { id: string; cursor: { x: number; y: number } };

export const join = irpc.declare<(visitor: Visitor) => RemoteState<Record<string, Visitor>>>(
  'visitor.join',
  {
    seed: () => ({}),
    keepAlive: true,
  }
);
```

:::tip[What we learn]
`declare` defines the contract once — the same stub becomes the server implementation with `construct` and the client call with `once()`, with the types flowing to both sides.
:::

Implement it — the stream stays open and pushes every change to connected clients:

```typescript
// src/pages/constructor.ts
import { mutable } from '@airlib/react/core';
import { stream } from '@irpclib/irpc';
import { irpc } from '../api.js';
import { type Visitor, join } from './function.js';

const VISITORS = mutable({} as Record<string, Visitor>);

irpc.construct(join, (visitor: Visitor) =>
  stream((state) => {
    VISITORS[visitor.id] = visitor;
    state.data = VISITORS;

    return () => {
      delete VISITORS[visitor.id];
    };
  })
);
```

:::tip[What we learn]
Joining is just mutating the shared state — writing the visitor into `VISITORS` broadcasts the change to every connected client. Returning a cleanup function is all it takes to leave: it runs when the page closes or the connection drops, removing the visitor.
:::

Wire the routers into the worker:

:::code-group

```typescript [React]
// src/worker.ts
import { createApp } from '@airlib/react/ssr';
import { HTTPRouter } from '@irpclib/http/router';
import { WebSocketRouter } from '@irpclib/ws/router';
import { httpTransport, wsTransport } from './api.js';
import App from './app.js';
import router from './router.js';

const httpRouter = new HTTPRouter(httpTransport);
const wsRouter = new WebSocketRouter(wsTransport);

export default createApp(router, App, { httpRouter, wsRouter });
```

```typescript [SolidJS]
// src/worker.ts
import { createApp } from '@airlib/solid/ssr';
import { HTTPRouter } from '@irpclib/http/router';
import { WebSocketRouter } from '@irpclib/ws/router';
import { httpTransport, wsTransport } from './api.js';
import App from './app.js';
import router from './router.js';

const httpRouter = new HTTPRouter(httpTransport);
const wsRouter = new WebSocketRouter(wsTransport);

export default createApp(router, App, { httpRouter, wsRouter });
```

:::

Then subscribe from a page — `stub.once()` joins the stream, and `<Snippet>` keeps the updates fine-grained, so only the value re-renders:

:::code-group

```tsx [React]
import { page, Snippet } from '@airlib/react';
import { indexRoute } from './route.js';
import { join } from './function.js';

export default page(indexRoute).render(() => {
  const visitors = join.once({ id: 'me', cursor: { x: 0, y: 0 } });

  return <Snippet>{() => `${Object.keys(visitors.data).length} online`}</Snippet>;
});
```

```tsx [SolidJS]
import { page, Snippet } from '@airlib/solid';
import { indexRoute } from './route.js';
import { join } from './function.js';

export default page(indexRoute).render(() => {
  const visitors = join.once({ id: 'me', cursor: { x: 0, y: 0 } });

  return <Snippet>{() => `${Object.keys(visitors.data).length} online`}</Snippet>;
});
```

:::

:::tip[What we learn]
`once()` joins the stream and returns a live `RemoteState` — `visitors.data` updates as the server pushes changes. `<Snippet>` re-renders only the value, so the count updates without re-rendering the page.
:::

## **Browser States**

The browser is reactive state too. Want the UI to follow the pointer, or a page to react to a keypress — without a single event listener. `LIVE_CURSOR` and `LIVE_KEYBOARD` expose the mouse and keyboard as live state; read them in a `<Show>` or `<Snippet>` and the UI updates as they change.

Track the pointer declaratively — the cursor follows the mouse, and the button state swaps the icon:

:::code-group

```tsx [React]
import { Show } from '@airlib/react';
import { LIVE_CURSOR } from '@airlib/react/browser';
import mouse from '../assets/cursor.svg';
import mouseDown from '../assets/cursor-down.svg';

<Show when={() => LIVE_CURSOR.x && LIVE_CURSOR}>
  {({ x, y, button }) => (
    <img
      className="user-cursor"
      src={button === 'left' ? mouseDown : mouse}
      alt="cursor"
      style={{ transform: `translate3d(${x}px, ${y}px, 0)` }}
    />
  )}
</Show>
```

```tsx [SolidJS]
import { Show } from '@airlib/solid';
import { LIVE_CURSOR } from '@airlib/solid/browser';
import mouse from '../assets/cursor.svg';
import mouseDown from '../assets/cursor-down.svg';

<Show when={() => LIVE_CURSOR.x && LIVE_CURSOR}>
  {({ x, y, button }) => (
    <img
      class="user-cursor"
      src={button === 'left' ? mouseDown : mouse}
      alt="cursor"
      style={{ transform: `translate3d(${x}px, ${y}px, 0)` }}
    />
  )}
</Show>
```

:::

React to a keypress the same way — a shortcut badge that appears while the combination is held:

:::code-group

```tsx [React]
import { Show } from '@airlib/react';
import { LIVE_KEYBOARD } from '@airlib/react/browser';

<Show when={() => (LIVE_KEYBOARD.is('ctrl', 's') || LIVE_KEYBOARD.is('meta', 's')) && LIVE_KEYBOARD}>
  {({ key }) => <p className="save-toast">Saved via shortcut ({key})!</p>}
</Show>
```

```tsx [SolidJS]
import { Show } from '@airlib/solid';
import { LIVE_KEYBOARD } from '@airlib/solid/browser';

<Show when={() => (LIVE_KEYBOARD.is('ctrl', 's') || LIVE_KEYBOARD.is('meta', 's')) && LIVE_KEYBOARD}>
  {({ key }) => <p class="save-toast">Saved via shortcut ({key})!</p>}
</Show>
```

:::

:::tip[What we learn]
No listeners, no subscriptions — the LIVE objects are state. Reading them inside `<Show>` tracks the pointer position, buttons, and modifiers automatically, and the rendered output updates when they change. They need `acceptInteractions()` in the client entry to be active.
:::

Beyond the cursor and keyboard: live scroll, selection, drag & drop, network, media, and geolocation — see [Browser Utilities](/docs/user-interface/browser).

## **Static Site Generation**

Pre-render pages to plain HTML at build time. Mark routes `static` and the server build pre-renders them — requests are served straight from disk (or a pluggable cache adapter) with proper `Cache-Control` headers.

Mark the route itself `static` in the folder's `route.ts` — the docs page never changes, so it's served as a plain file:

```typescript
// src/pages/mdx/route.ts
import rootRoute from '../route.js';

export const docsRoute = rootRoute.route('/docs', { static: true });

export default docsRoute;
```

To pre-render the entire site, set it once on the router instead:

```typescript
// src/router.ts
const router = createRouter({ static: true });
```

The build writes the pre-rendered pages as plain HTML into `dist/client` — one file per route (`/docs` → `dist/client/docs.html`). Deploy that folder to any static host — Netlify, Cloudflare Pages, GitHub Pages, an S3 bucket — and the site is live.

Only URLs known at build time can be pre-rendered — a dynamic route like `/products/:id` is skipped, because its pages aren't discoverable until they exist.

## **Incremental Static Regeneration**

You want dynamic pages served as static HTML. Build-time pre-rendering can't cover them — the URLs don't exist yet. Mark the route `static` and it pre-renders on demand: the first request to each URL renders it and writes it to disk, and every later request is served from that file:

```typescript
// src/pages/products/[id]/route.ts
import productsRoute from '../route.js';

export const productsDynamicRoute = productsRoute.route('/:id', { static: true });

export default productsDynamicRoute;
```

When the content changes — a price update, a stock change — a file served from disk stays stale. Give the route a `maxAge`: the file is served until it's older than `maxAge`, then the next request re-renders it and refreshes the file. New content shows up without a rebuild:

```typescript
// src/pages/products/[id]/route.ts
import productsRoute from '../route.js';

export const productsDynamicRoute = productsRoute.route('/:id', { static: { maxAge: 3600 } });

export default productsDynamicRoute;
```

## **Ship Zero JavaScript**

Ship pages with zero JavaScript and no hydration script — the build strips every script from the output, so browsers receive pure HTML, Astro-style, while you keep the full authoring experience:

```typescript
// vite.config.ts
import { airPages } from '@airlib/vite';

export default defineConfig({
  plugins: [airPages({ noscript: true })],
});
```

## **Manual Setup**

Install the framework and the plugin, create the entry files, then run.

### **1. Install Dependencies**

:::code-group

```bash [React]
npm install @airlib/react react react-dom
npm install -D @airlib/vite @vitejs/plugin-react typescript vite @types/react @types/react-dom
```

```bash [SolidJS]
npm install @airlib/solid solid-js
npm install -D @airlib/vite vite-plugin-solid typescript vite
```

:::

### **2. Create the HTML Shell**

Every page renders into one `index.html`. Two comments mark where the server injects the document head and the rendered page:

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <!--ssr-head-->
  </head>
  <body>
    <div id="root" style="display: contents;"><!--ssr-outlet--></div>
    <script type="module" src="/src/client.tsx"></script>
  </body>
</html>
```

### **3. Create the Router**

The router is the single instance every route in the app is created from:

:::code-group

```typescript [React]
// src/router.ts
import { createRouter } from '@airlib/react';

const router = createRouter();
export default router;
```

```typescript [SolidJS]
// src/router.ts
import { createRouter } from '@airlib/solid';

const router = createRouter();
export default router;
```

:::

:::tip[What we learn]
A folder defines a URL. `airPages()` watches `src/pages` and generates a `route.ts` per folder — `src/pages/route.ts` exports the `rootRoute` and `indexRoute` your layout and page import. You write pages, not route trees.
:::

### **4. Create the App Entry**

The entry both the client hydrates and the worker renders. It renders the root layout with the router:

:::code-group

```tsx [React]
// src/app.tsx
import { type AppEntry, UIRouter } from '@airlib/react';
import RootLayout from './pages/layout.tsx';
import router from './router.ts';

export default (({ url }) => (
  <UIRouter router={router} root={RootLayout} url={url} />
)) satisfies AppEntry;
```

```tsx [SolidJS]
// src/app.tsx
import { type AppEntry, UIRouter } from '@airlib/solid';
import RootLayout from './pages/layout.tsx';
import router from './router.ts';

export default (({ url }) => (
  <UIRouter router={router} root={RootLayout} url={url} />
)) satisfies AppEntry;
```

:::

`RootLayout` is the root layout — the structure every page renders inside, created in the Layouts section below.

### **5. Create the Client Entry**

Hydrate the app in the browser:

:::code-group

```tsx [React]
// src/client.tsx
import '@airlib/react/client'; // must be first import

import { hydrateRoot } from 'react-dom/client';
import { acceptInteractions } from '@airlib/react/browser';
import App from './app.js';
import router from './router.js';

router.activate(window.location.href).then(() => {
  hydrateRoot(document.getElementById('root')!, <App />);
}).then(() => acceptInteractions());
```

```tsx [SolidJS]
// src/client.tsx
import '@airlib/solid/client'; // must be first import

import { hydrate } from 'solid-js/web';
import { acceptInteractions } from '@airlib/solid/browser';
import App from './app.js';
import router from './router.js';

router.activate(window.location.href).then(() => {
  hydrate(() => <App />, document.getElementById('root')!);
}).then(() => acceptInteractions());
```

:::

:::tip[What we learn]
- The server already sent a complete page — the user sees the full content before any JavaScript runs.
- `activate()` runs the route again on the client, re-checking its guards and providers — if a guard no longer passes (an auth check expired, a provider failed), the client follows the redirect instead of hydrating a page that shouldn't render.
- `hydrate()` re-constructs the existing DOM instead of building it from scratch — the client rebuilds exactly what the server rendered, so the two can never mismatch.
- `acceptInteractions()` is optional — it enables the live browser objects (`LIVE_CURSOR`, `LIVE_KEYBOARD`, …; see [Browser Utilities](/docs/user-interface/browser)). Omit it and the page still works; the live objects just stay off.
:::

### **6. Create the Worker**

The server entry — one worker that serves SSR and static assets:

:::code-group

```typescript [React]
// src/worker.ts
import { createApp } from '@airlib/react/ssr';
import App from './app.js';
import router from './router.js';

export default createApp(router, App);
```

```typescript [SolidJS]
// src/worker.ts
import { createApp } from '@airlib/solid/ssr';
import App from './app.js';
import router from './router.js';

export default createApp(router, App);
```

:::

:::tip[What we learn]
- The worker exposes a standard `fetch()` handler — any runtime that speaks web standards (Bun, Node, Deno, Cloudflare) can hook into it with minimal setup.
- On Bun, `bun run dist/server/worker.js` just works, because the file exports the `fetch()` handler directly.
:::

### **7. Configure Vite**

Add `airPages()` — your framework is detected automatically:

:::code-group

```typescript [React]
// vite.config.ts
import { airPages } from '@airlib/vite';
import react from '@vitejs/plugin-react';
import { defineConfig } from 'vite';

export default defineConfig({
  plugins: [react(), airPages()],
});
```

```typescript [SolidJS]
// vite.config.ts
import { airPages } from '@airlib/vite';
import { defineConfig } from 'vite';
import solid from 'vite-plugin-solid';

export default defineConfig({
  plugins: [solid({ ssr: true }), airPages()],
});
```

:::

### **8. Run It**

Wire the scripts, then start the dev server:

```json
{
  "scripts": {
    "dev": "vite",
    "build:client": "vite build --outDir dist/client",
    "build:server": "vite build --ssr --outDir dist/server",
    "build": "bun run build:client && bun run build:server",
    "start": "bun run dist/server/worker.js"
  }
}
```

Run `bun run dev` (or `npm run dev`) once so the plugin generates the per-folder `route.ts` files. While it runs, an empty `page.tsx` you create in any folder is filled with a working starter. Then add the layout and the index page in the next two sections and the app renders.

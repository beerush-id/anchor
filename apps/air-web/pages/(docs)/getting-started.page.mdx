# Getting Started with AirLib

AirLib is a universal full-stack TypeScript framework: state, routing, remote functions, and server rendering in one reactive system. The core is framework-agnostic — the same logic runs in React or SolidJS, and only the view-layer import differs.

:::tip[Need to install or scaffold first?]
If you haven't created your project yet, check out the [Installation Guide](/docs/installation) to scaffold instantly with `create airlib` or add AirLib manually to an existing Vite setup.
:::

## Assisted File-Based Routing

AirLib bridges the gap between **file-system convenience** and **programmatic control** through the `@airlib/vite` plugin (`airPages()`):

- **Automatic Route Scaffolding** — When the dev server runs, creating an empty `page.tsx` or `layout.tsx` in any folder automatically generates and wires the local `route.ts` file for you, including starter boilerplate.
- **Zero Black Boxes** — Once generated, the code is 100% yours. AirLib does not hide route trees inside opaque compiler virtual modules.
- **Full Programmatic Power** — Having an explicit `route.ts` alongside your component allows you to attach typed access guards (`.guard()`), asynchronous data loaders (`.provide()`), and custom route metadata with full TypeScript autocomplete.

Every scaffolded `route.ts` contains an AirLib-managed block and clean user exports:

```typescript
// pages/route.ts
import router from '@/src/router.js';

/** AirLib managed */
const route = router.route();
const indexRoute = route.route('/');
/** AirLib managed */

export const rootRoute = route;
export const rootIndexRoute = indexRoute;

export default rootRoute;
```

## Layouts

Layouts define the persistent shell of your application. The layout stays mounted across navigation—while page content swaps dynamically inside `{children}`.

### The Root Layout

The root layout wraps your entire application. It holds global navigation, headers, and footers that remain mounted across all route transitions. Create `pages/layout.tsx`:

:::code-group[Root Layout]{group="framework"}

```tsx [React] name="react"
import { page } from '@airlib/react';
import { rootRoute } from './route.js';

export default page(rootRoute).render(({ children }) => (
  <>
    <header>My AirLib App</header>
    <main>{children}</main>
    <footer>© 2026 AirLib</footer>
  </>
));
```

```tsx [SolidJS] name="solid"
import { page } from '@airlib/solid';
import { rootRoute } from './route.js';

export default page(rootRoute).render(({ children }) => (
  <>
    <header>My AirLib App</header>
    <main>{children}</main>
    <footer>© 2026 AirLib</footer>
  </>
));
```

:::

:::tip[What we learn]
The layout renders once and stays mounted — `{children}` is where the matched page renders, so navigation swaps only the page inside the frame, not the frame itself.
:::

### Nested Layouts

Nested sections can declare their own sub-layouts. Creating `pages/products/layout.tsx` wraps all child routes under `/products` inside a scoped sidebar frame while remaining nested inside the root layout:

:::code-group[Products Layout]{group="framework"}

```tsx [React] name="react"
import { page } from '@airlib/react';
import { productsRoute } from './route.js';

export default page(productsRoute).render(({ children }) => (
  <div>
    <aside>Categories</aside>
    <main>{children}</main>
  </div>
));
```


## Pages

Pages define the content and document metadata for specific URL paths.

### The Root Index Page

`/` is the home page. Create `pages/page.tsx` with document metadata:

:::code-group[Root Page]{group="framework"}

```tsx [React] name="react"
import { Head, page } from '@airlib/react';
import { rootIndexRoute } from './route.js';

export default page(rootIndexRoute).render(() => (
  <>
    <Head meta={{ title: 'Home | AirLib', description: 'Welcome to my AirLib application' }} />
    <h1>Welcome Home</h1>
  </>
));
```

```tsx [SolidJS] name="solid"
import { Head, page } from '@airlib/solid';
import { rootIndexRoute } from './route.js';

export default page(rootIndexRoute).render(() => (
  <>
    <Head meta={{ title: 'Home | AirLib', description: 'Welcome to my AirLib application' }} />
    <h1>Welcome Home</h1>
  </>
));
```

:::

:::tip[What we learn]
`<Head>` doesn't render in the page — it injects the title, the meta description, and the social tags into the document head, and it works the same during SSR.
:::

### Named Pages

Single-file routes do not need a dedicated directory: `pages/sale.page.tsx` renders directly at `/sale`:

:::code-group[Named Sale Page]{group="framework"}

```tsx [React] name="react"
import { page } from '@airlib/react';

export default page(saleRoute).render(() => <h1>Sale</h1>);
```

```tsx [SolidJS] name="solid"
import { page } from '@airlib/solid';

```

:::

:::note[File Organization Convention]
Named pages (`[name].page.tsx` / `[name].page.mdx`) and directory pages (`[name]/page.tsx`) are purely file organization conventions—neither is universally better. For simple, self-contained endpoints, named files keep your project tree flat. For routes with complex logic, multiple sub-components, or local assets, a dedicated folder isolates those files and avoids cluttering parent directories.
:::

### Markdown Pages

For content-rich documents (documentation, guides, blogs), use MDX. Creating `page.mdx` lets you write rich prose with live embedded JSX components, with frontmatter defining route metadata:

```mdx
---
title: FAQ
description: Frequently asked questions about the store
---

# FAQ

Welcome back, {$state.data.user.name}!
```

A Markdown page still runs through the same route pipeline as a TSX page — route state works in the markup, and components work inside the prose.

:::tip[What we learn]
`$state` is the route's live reactive state, available right in the markup — when the data changes, the page updates.
:::

### Dynamic & Catch-all Pages

A folder in square brackets is a dynamic segment — `pages/products/[id]/page.tsx` renders at `/products/:id`, and the segment is available as `state.params.id`:

:::code-group[Dynamic Product Route]{group="framework"}

```tsx [React] name="react"
import { page } from '@airlib/react';
import { productsDynamicRoute } from './route.js';

export default page(productsDynamicRoute).render(({ state }) => (
  <h1>{state.params.id}</h1>
));
```

```tsx [SolidJS] name="solid"
import { page } from '@airlib/solid';
import { productsDynamicRoute } from './route.js';

export default page(productsDynamicRoute).render(({ state }) => (
  <h1>{state.params.id}</h1>
));
```

:::

A `[...rest]` folder is a catch-all — the rare route whose URL you can't know upfront, because the path itself is undeterministic: a file browser, a wiki, an import path. `pages/[...rest]/page.tsx` matches any path under it, and the segments arrive in `state.params['*']`:

:::code-group[Catch-all Dynamic Route]{group="framework"}

```tsx [React] name="react"
import { page } from '@airlib/react';
import { catchAllRoute } from './route.js';

export default page(catchAllRoute).render(({ state }) => (
  <h1>{state.params['*'].join(' / ')}</h1>
));
```

```tsx [SolidJS] name="solid"
import { page } from '@airlib/solid';
import { catchAllRoute } from './route.js';

export default page(catchAllRoute).render(({ state }) => (
  <h1>{state.params['*'].join(' / ')}</h1>
));
```

:::

:::tip[What we learn]
A catch-all isn't for missing pages — it's for paths whose shape you can't predict, so the route can't declare named segments. Every remaining segment lands in `state.params['*']` as an array, and the page interprets the path itself.
:::

## Building Navigation

To generate dynamic navigation menus without manual list maintenance, import the route manifest generated by `airPages()`:

```tsx
import routes from '@airlib-cache/manifest'; // generated by airPages
import { Link } from '@airlib/react';

export function Nav() {
  return (
    <nav>
      {routes.filter((r) => r.path !== '/').map(({ path, route }) => (
        <Link key={path} to={route}>
          {route.metadata.label ?? path}
        </Link>
      ))}
    </nav>
  );
}
```

A section sidebar is the same manifest scoped to a folder: `import docsRoutes from '@airlib-cache/manifest/docs'`. Route metadata keys are typed through `AirRouteMeta` in `global.d.ts`:

```ts
// global.d.ts
/// <reference types="@airlib/vite/ambient" />

interface AirRouteMeta {
  name?: string;
  label?: string;
}
```

## Remote Functions

When your application requires server logic, IRPC provides end-to-end type-safe remote procedure calls without manual API client code or schema boilerplate.

An IRPC function works anywhere:
- **As a standard async Promise** — Call `await getStats()` in route guards, providers, or actions.
- **As a reactive UI reader** — Call `getStats.once()` inside components for fine-grained `data`, `status`, and `error` tracking.
- **As a real-time stream** — Return `stream()` on the server to push live or progressive updates over HTTP.

### Declare the Function Contract

Declare the typed procedure using the pre-configured `irpc` package from `src/api.ts`:

```typescript
// src/dashboard.api.ts
import { irpc } from './api.js';

export type Stats = { totalSales: string; orders: number };

export const getStats = irpc.declare<() => Promise<Stats>>('dashboard.stats');
```

:::tip[What we learn]
`declare` defines the function signature once. The same stub is used to implement the backend with `irpc.construct()`, invoke standard Promises (`await getStats()`), or subscribe reactively in components with `getStats.once()`.
:::

### Implement on the Server

Bind the backend implementation using `irpc.construct()`:

```typescript
// server/dashboard.ts
import { irpc } from '../src/api.js';
import { getStats } from '../src/dashboard.api.js';

irpc.construct(getStats, async () => {
  return await db.fetchDashboardStats();
});
```

### Reactive Component Calling

Invoke the procedure in a component with `.once()`. It returns a reactive reader that tracks network `status` and `data` automatically without manual `fetch` or effect hooks:

:::code-group[Reactive RPC Call]{group="framework"}

```tsx [React] name="react"
import { page, Show } from '@airlib/react';
import { rootIndexRoute } from './route.js';
import { getStats } from '@/dashboard.api.js';

export default page(rootIndexRoute).render(() => {
  const stats = getStats.once();

  return (
    <div>
      <Show when={() => stats.data}>
        {({ totalSales, orders }) => (
          <div>
            <h1>{totalSales} in sales</h1>
            <p>{orders} orders</p>
          </div>
        )}
      </Show>
    </div>
  );
});
```

```tsx [SolidJS] name="solid"
import { page, Show } from '@airlib/solid';
import { rootIndexRoute } from './route.js';
import { getStats } from '@/dashboard.api.js';

            <h1>{totalSales} in sales</h1>

          </div>

```

### Real-Time Streaming

When you need continuous live updates (presence counters, live chat, cursor sync) or progressive chunks, return `stream()` inside `irpc.construct()`:

```typescript
// src/visitor.api.ts
import type { RemoteState } from '@irpclib/irpc';
import { irpc } from './api.js';

export type Visitor = { id: string; cursor: { x: number; y: number } };
export type JoinFn = (visitor: Visitor) => RemoteState<Record<string, Visitor>>;

export const join = irpc.declare<JoinFn>('visitor.join', {
  seed: () => ({}),
  keepAlive: true,
});
```

```typescript
// server/visitor.ts
import { mutable } from '@airlib/core';
import { stream } from '@irpclib/irpc';
import { irpc } from '../src/api.js';
import { type Visitor, join } from '../src/visitor.api.js';

const VISITORS = mutable({} as Record<string, Visitor>);

irpc.construct(join, (visitor: Visitor) => stream((state) => {
  VISITORS[visitor.id] = visitor;
  state.data = VISITORS;

  return () => {
    delete VISITORS[visitor.id];
  };
}));
```

```tsx
// pages/page.tsx
const visitors = join.once({ id: 'me', cursor: { x: 0, y: 0 } });

<Snippet>{() => `${Object.keys(visitors.data ?? {}).length} online`}</Snippet>
```

## Guards & Providers

Route protection and data fetching belong at the routing layer. Guards authenticate or redirect before components mount, while providers fetch asynchronous data so views receive typed data immediately.

### Guards

To secure private sections (such as an admin dashboard), attach `.guard()` to the route. Throwing a redirect halts navigation before child components mount:

:::code-group[Guarded Dashboard Route]{group="framework"}

```ts [React] name="react"
// pages/dashboard/route.ts
import { redirect } from '@airlib/react';
import { loginRoute } from '../login/route.js';
import rootRoute from '../route.js';

/** AirLib managed */
const route = rootRoute.route('/dashboard');
const indexRoute = route.route('/');
/** AirLib managed */

export const dashboardRoute = route.guard(async () => {
  if (!(await isLoggedIn())) throw redirect(loginRoute);
});

export const dashboardIndexRoute = indexRoute;

export default dashboardRoute;
```

```ts [SolidJS] name="solid"
// pages/dashboard/route.ts
import { redirect } from '@airlib/solid';
import { loginRoute } from '../login/route.js';
import rootRoute from '../route.js';

/** AirLib managed */
const route = rootRoute.route('/dashboard');
const indexRoute = route.route('/');
/** AirLib managed */

export const dashboardRoute = route.guard(async () => {
  if (!(await isLoggedIn())) throw redirect(loginRoute);
});

export const dashboardIndexRoute = indexRoute;

export default dashboardRoute;
```

:::

:::tip[What we learn]
The guard lives on the route, not on the page — the visitor never sees the page, not even a flash. A guard on a folder's route protects every page under that folder, so one check secures a whole section.
:::

### Providers

When a route requires server data before rendering, attach `.provide()`. Navigation awaits the data and passes typed results to the page component:

:::code-group[Data-Provided Route]{group="framework"}

```ts [React] name="react"
// pages/dashboard/route.ts
import { redirect } from '@airlib/react';
import { getStats } from '@/dashboard.api.js';
import { loginRoute } from '../login/route.js';
import rootRoute from '../route.js';

/** AirLib managed */
const route = rootRoute.route('/dashboard');
const indexRoute = route.route('/');
/** AirLib managed */

export const dashboardRoute = route
  .guard(async () => {
    if (!(await isLoggedIn())) throw redirect(loginRoute);
  })
  .provide('stats', async () => {
    return await getStats();
  });

export const dashboardIndexRoute = indexRoute;

export default dashboardRoute;
```

```ts [SolidJS] name="solid"
// pages/dashboard/route.ts
import { redirect } from '@airlib/solid';
import { getStats } from '@/dashboard.api.js';
import { loginRoute } from '../login/route.js';

```

:::tip[What we learn]
An async provider makes navigation wait for its data — the user stays on the current page until it resolves (on the initial load, that's the browser's native loading indicator). `state.data` holds this route's providers only; child pages and layouts read the merged tree — every provider up the chain — via `context.data`.

### Provider & Navigation Feedback

AirLib provides fine-grained reactive status for both individual data providers and global navigation progress:

- **Provider Resolution State** — `state.resolving` is a reactive `Set<string>`. Check `state.resolving.has('stats')` to display a skeleton loader or spinner while a specific provider is fetching:

```tsx
<Show when={() => state.resolving.has('stats')}>
  <p className="loading-spinner">Refreshing stats...</p>
</Show>
```

- **Global Transition Progress** — `router.state.progress` and `router.state.steps` track the overall navigation progress across all executed guards and providers:

```tsx
<Snippet>
  {() => (
    <div
      class="progress-bar"
      style={{ width: `${(router.state.progress / router.state.steps) * 100}%` }}
    />
  )}
</Snippet>
```

### Progressive Data Loading

Fetching data inside nested client components often leads to **request waterfalls**—where each component triggers its own sequential HTTP request over high-latency networks.

AirLib eliminates client waterfalls by combining **parallel server execution** with **progressive streaming over a single connection**:

1. **Single Client Stream** — The browser opens one stream via `loadDashboard.once()`.
2. **Parallel Server Execution** — The server dispatches all independent database queries concurrently over internal sub-millisecond networks.
3. **Progressive UI Updates** — As each server task resolves, it pushes chunks down the open stream, updating the reactive state and rendering widgets progressively without blocking on the slowest query:

```typescript
// src/dashboard.api.ts
import type { RemoteState } from '@irpclib/irpc';
import { irpc } from './api.js';

export type DashboardData = {
  sales?: SalesSummary;
  orders?: Order[];
  alerts?: Alert[];
};

export type LoadDashboardFn = () => RemoteState<DashboardData>;

export const loadDashboard = irpc.declare<LoadDashboardFn>('dashboard.load', {
  seed: () => ({}),
  keepAlive: true,
});
```

```typescript
// server/dashboard.ts
import { stream } from '@irpclib/irpc';
import { irpc } from '../src/api.js';
import { loadDashboard } from '../src/dashboard.api.js';

irpc.construct(loadDashboard, () => stream((state, resolve) => {
  const sales = fetchSales().then((sales) => {
    state.data.sales = sales;
  });
  const orders = fetchOrders().then((orders) => {
    state.data.orders = orders;
  });
  const alerts = fetchAlerts().then((alerts) => {
    state.data.alerts = alerts;
  });

  Promise.all([sales, orders, alerts]).then(() => resolve());
}));
```

```tsx
// pages/dashboard/page.tsx
import { page, Show } from '@airlib/react';
import { dashboardIndexRoute } from './route.js';
import { loadDashboard } from '@/dashboard.api.js';

export default page(dashboardIndexRoute).render(() => {
  const dashboard = loadDashboard.once();

  return (
    <div>
      <Show when={() => dashboard.data?.sales}>
        {(sales) => <SalesSummary sales={sales} />}
      </Show>
      <Show when={() => dashboard.data?.orders}>
        {(orders) => <OrdersTable orders={orders} />}
      </Show>
      <Show when={() => dashboard.data?.alerts}>
        {(alerts) => <AlertsFeed alerts={alerts} />}
      </Show>
    </div>
  );
});
```

:::tip[Automatic Request Batching]
You do not have to write dedicated wrapper functions just to prevent network overhead. If you call multiple atomic procedures in the same tick (`const sales = getSales.once(); const orders = getOrders.once();`), IRPC automatically batches them into a single network payload behind the scenes. Using individual batched calls or a unified progressive stream is pure architectural preference.
:::

## Browser States

The browser is reactive state too. Want the UI to follow the pointer, or a page to react to a keypress — without a single event listener. `LIVE_CURSOR` and `LIVE_KEYBOARD` expose the mouse and keyboard as live state; read them in a `<Show>` or `<Snippet>` and the UI updates as they change.

Track the pointer declaratively — the cursor follows the mouse, and the button state swaps the icon:

:::code-group[Live Cursor Tracking]{group="framework"}

```tsx [React] name="react"
import { Show } from '@airlib/react';
import { LIVE_CURSOR } from '@airlib/react/browser';
import mouse from '../assets/cursor.svg';
import mouseDown from '../assets/cursor-down.svg';

<Show when={() => LIVE_CURSOR.x && LIVE_CURSOR}>
  {({ x, y, button }) => (
    <img
      className="user-cursor"
      src={button === 'left' ? mouseDown : mouse}
      alt="cursor"
      style={{ transform: `translate3d(${x}px, ${y}px, 0)` }}
    />
  )}
</Show>
```

```tsx [SolidJS] name="solid"
import { Show } from '@airlib/solid';
import { LIVE_CURSOR } from '@airlib/solid/browser';
import mouse from '../assets/cursor.svg';
import mouseDown from '../assets/cursor-down.svg';
```

## Static Site Generation

Pre-render pages to plain HTML at build time. Mark routes `static` and the server build pre-renders them — requests are served straight from disk with proper `Cache-Control` headers.

Mark the route itself `static` in the folder's `route.ts` — the docs page never changes, so it's served as a plain file:

```typescript
// pages/docs/route.ts
import rootRoute from '../route.js';

/** AirLib managed */
const route = rootRoute.route('/docs');
const indexRoute = route.route('/');
/** AirLib managed */

export const docsRoute = route.config({ static: true });
export const docsIndexRoute = indexRoute;

export default docsRoute;
```

To pre-render the entire site, set it once on the router instead:

```typescript
// src/router.ts
const router = createRouter({ static: true });
```

The build writes the pre-rendered pages as plain HTML into `dist/client` — one file per route (`/docs` → `dist/client/docs.html`). Deploy that folder to any static host — Netlify, Cloudflare Pages, GitHub Pages, an S3 bucket — and the site is live.

Only URLs known at build time can be pre-rendered — a dynamic route like `/products/:id` is skipped, because its pages aren't discoverable until they exist.

## Incremental Static Regeneration

You want dynamic pages served as static HTML. Build-time pre-rendering can't cover them — the URLs don't exist yet. Mark the route `static` and it pre-renders on demand: the first request to each URL renders it and writes it to disk, and every later request is served from that file:

```typescript
// pages/products/[id]/route.ts
import productsRoute from '../route.js';

/** AirLib managed */
const route = productsRoute.route('/:id');
const indexRoute = route.route('/');
/** AirLib managed */

export const productsDynamicRoute = route.config({ static: true });
export const productsDynamicIndexRoute = indexRoute;

export default productsDynamicRoute;
```

When the content changes — a price update, a stock change — a file served from disk stays stale. Give the route a `maxAge`: the file is served until it's older than `maxAge`, then the next request re-renders it and refreshes the file. New content shows up without a rebuild:

```typescript
// pages/products/[id]/route.ts
import productsRoute from '../route.js';

/** AirLib managed */
const route = productsRoute.route('/:id');
const indexRoute = route.route('/');
/** AirLib managed */

export const productsDynamicRoute = route.config({ static: { maxAge: 3600 } });
export const productsDynamicIndexRoute = indexRoute;

export default productsDynamicRoute;
```

## Ship Zero JavaScript

Ship pages with zero JavaScript and no hydration script — the build strips every script from the output, so browsers receive pure HTML, Astro-style, while you keep the full authoring experience:

```typescript
// vite.config.ts
import { airPages } from '@airlib/vite';

export default defineConfig({
  plugins: [airPages({ noscript: true })],
});
```

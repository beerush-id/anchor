# AirLib Form

**Zero-Boilerplate, Schema-Driven Reactive Forms**

Forms are the primary medium of user interaction on the web. They capture user input, enforce data integrity through business rules, track user mutations, and coordinate asynchronous submission lifecycles.

:::details[The traditional form dilemma]
In modern web applications, handling forms often means navigating repetitive boilerplate and fragmented tooling:

- Manually writing imperative `onChange`, `onBlur`, and `value` bindings across every input.
- Synchronizing validation rules across UI components, client schemas, and backend payloads.
- Implementing custom state machines for dirty tracking, field touched states, and error arrays.
- Coordinating multi-step submission states (`idle`, `pending`, `success`, `error`) and input-locking logic.
- Managing coarse-grained component re-renders where a keystroke in one input forces the entire form to re-evaluate.

Most form libraries address this by adding new abstractions — custom register hooks, controller wrappers, and field arrays — which trade native HTML simplicity for framework-specific DSLs.
:::

When form architecture demands dozens of lines of glue code for everyday fields, the tooling slows down product development.

:::tip[What if:]
**Your Zod schema is the single source of truth, and the form engine derives the rest?**
:::

AirLib Form aligns form development with native web principles: define your **Zod schema once**, and the engine autonomously derives **fine-grained reactivity**, **runtime validation**, **error collections**, **dirty-state tracking**, **cross-field matching**, and the **submit lifecycle**.

:::code-group{group="framework"}
```tsx [React] name="react" executable
import { z } from 'zod';
import { setup, mutable } from '@airlib/react';
import { createForm, TextInput, EmailInput, Textarea } from '@airlib/react-form';

const userSchema = z.object({
  name: z.string().min(3, 'Name is too short'),
  email: z.string().email('Invalid email'),
  bio: z.string().max(160, 'Bio is too long').optional(),
});

const UserForm = createForm(userSchema);

const ProfileEditor = setup(() => {
  const profile = mutable({ name: '', email: '', bio: '' });

  return (
    <UserForm value={profile} onSubmit={(data) => console.log('Saved:', data)}>
      <UserForm.Field name="name" label="Name">
        <TextInput placeholder="Enter name" />
      </UserForm.Field>

      <UserForm.Field name="email" label="Email">
        <EmailInput placeholder="Enter email" />
      </UserForm.Field>

      <UserForm.Field name="bio" label="Bio">
        <Textarea placeholder="Tell us about yourself" />
      </UserForm.Field>

      <div className="flex gap-2">
        <UserForm.Reset>Reset</UserForm.Reset>
        <UserForm.Submit className="flex-1">Save</UserForm.Submit>
      </div>
    </UserForm>
  );
});
```

With AirLib Form, you don't need to write repetitive form glue code to build forms that are **strictly typed**, **fine-grained reactive**, and **accessible**—delivering complete **validation**, **dirty tracking**, and **submission lifecycles** with zero boilerplate.

:::tip[Schema as the Single Source of Truth]
The Zod schema is the **contract**. Every field name, type constraint, and error message is derived automatically—catching typos (`name="typo"`) at compile time and validating mutations with zero runtime glue code.
:::

## Architecture

AirLib Form is split into two modular layers:

### Core Engine

The core package `@airlib/form` is framework-agnostic. It handles:

- **Schema validation** — Zod schemas define the contract, and the engine validates on every mutation
- **Reactive store** — Each field is a granular reactive signal, ensuring only the changed field updates
- **Change tracking** — Tracks which fields differ from baseline values, and by how much
- **Touched tracking** — Records mutated fields reliably, persisting until explicitly reset
- **Cross-field matching** — Evaluates equality checks or custom comparison logic as isolated signals
- **Submit lifecycle** — Coordinates `idle → pending → success/error` transitions with automatic input locking

### View Layer

The view layer (`@airlib/react-form`, `@airlib/solid-form`) provides framework-specific components that compose core signals into native UI:

- **Form** — Wraps children in form context and orchestrates submission
- **Field** — Connects field names to labels, error displays, and accessibility attributes
- **FieldList** — Exposes reactive arrays for dynamic lists with fine-grained tracking
- **Input components** — Pre-built, accessible inputs that auto-wire to the active form context
- **FormSubmit / FormReset** — Self-governing buttons that automatically track form readiness and dirty states

The core engine provides raw, unopinionated reactive state, while the view layer delivers ergonomic UI primitives. This separation means you get the same unified mental model across React, SolidJS, or headless environments.

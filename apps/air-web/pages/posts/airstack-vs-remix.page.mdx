# AirLib vs. Remix

:badge[Comparison]{variant="info"} :badge[Remix]{variant="neutral"} :badge[React Router]{variant="neutral"} :badge[AirLib]{variant="neutral"}

<a href="https://remix.run/" target="_blank" rel="noreferrer">Remix</a> (now unified with React Router) focuses heavily on Web Standards. It leverages HTTP caching, standard HTML `<form>` submissions, and nested routing to deliver a resilient user experience rooted in HTTP semantics.

**AirLib** (Anchor, IRPC, Reactive) takes a different approach. It pairs **assisted file-based routing** with isomorphic remote functions and a decoupled reactive state graph. It treats the UI as an independent reactive layer where components connect to backend logic through typed function calls and fine-grained subscriptions rather than manual HTTP request boundaries.

## Framework comparison

While both aim to deliver seamless full-stack React applications, their core paradigms and developer workflows differ fundamentally.

| Aspect | Remix (React Router) | AirLib |
|---|---|---|
| **Paradigm** | Web Standards & HTTP Request Boundaries | Unified Reactive Model (Decoupled UI & logic) |
| **Routing** | Compiler-driven file-system routing | Assisted file-based routing (Explicit route graph) |
| **Data Fetching** | Route Loaders & HTTP serialization | Route Loaders & Isomorphic Remote Functions |
| **Mutations** | Form Actions & FormData serialization | Isomorphic Remote Functions & Reactive State |
| **State** | URL search params & React Context | Fine-grained Reactive State |
| **Static Generation** | Build export & HTTP CDN caching | Granular SSG & On-Demand ISG |
| **Content & Markdown** | Custom plugins & route wrappers | Built-in Extended MDX (`.page.mdx`) |
| **Static Delivery** | Always ships client React runtime | Pure Zero-JavaScript static HTML option |
| **Deployment** | Platform-specific server adapters | Zero-adapter Universal SSR Worker |

## Application Setup

Both frameworks offer file-based routing workflows, but they manage transparency and route orchestration differently.

### Remix Setup

In Remix, the file system dictates the application structure. A root layout defines the HTML shell, and nested routes render into an `<Outlet />`.

```tsx
// app/root.tsx
import { Links, Meta, Outlet, Scripts, ScrollRestoration } from "@remix-run/react";

export default function Root() {
  return (
    <html lang="en">
      <head>
        <Meta />
        <Links />
      </head>
      <body>
        <div className="app">
          <header>My App</header>
          <Outlet />
        </div>
        <ScrollRestoration />
        <Scripts />
      </body>
    </html>
  );
}
```

```tsx
// app/routes/_index.tsx
export default function HomePage() {
  return (
    <main>
      <h1>Welcome to Remix</h1>
    </main>
  );
}
```

### AirLib Setup

AirLib bridges file-system simplicity with explicit, typed route orchestration through **assisted file-based routing**:

- **Drop-and-Go Pages** — Dropping a `page.tsx` or `layout.tsx` into `pages/` automatically establishes the route definition with typed exports and starter boilerplate.
- **Zero Black Boxes** — Routes are not opaque virtual modules hidden inside the compiler. The route definition lives directly in your project as plain TypeScript.
- **Full Programmatic Power** — Having an explicit route definition alongside your component gives you full control to attach access guards (`.guard()`), asynchronous data loaders (`.provide()`), and route metadata with full IDE autocomplete.

```tsx
// pages/layout.tsx
import { page } from '@airlib/react';
import { rootRoute } from './route.js';

export default page(rootRoute).render(({ children }) => (
  <div className="app">
    <header>My App</header>
    {children}
  </div>
));
```

```tsx
// pages/page.tsx
import { page } from '@airlib/react';
import { rootIndexRoute } from './route.js';

export default page(rootIndexRoute).render(() => (
  <main>
    <h1>Welcome to AirLib</h1>
  </main>
));
```

The accompanying `route.ts` maintains the typed route graph:

```typescript
// pages/route.ts
import router from '@/src/router.js';

/** AirLib managed */
const route = router.route();
const indexRoute = route.route('/');
/** AirLib managed */

export const rootRoute = route;
export const rootIndexRoute = indexRoute;

export default rootRoute;
```

## Rendering Paradigms

Modern applications require different rendering strategies depending on the data. Both frameworks support Server-Side Rendering (SSR), Client-Side Rendering (CSR), and Hybrid approaches.

### Pure Server-Side Rendering (SSR)

To fetch data on the server and render HTML before sending it to the client, Remix uses HTTP loaders, while AirLib uses route data providers.

#### Remix Loaders
Remix ties data fetching directly to the route via network endpoints. The `loader` runs exclusively on the server, and the data is serialized over the network and consumed via `useLoaderData`:

```tsx
// app/routes/users.tsx
import { json } from "@remix-run/node";
import { useLoaderData } from "@remix-run/react";
import { db } from "../db.server";

export async function loader() {
  const users = await db.users.findMany();
  return json({ users });
}

export default function UsersPage() {
  const { users } = useLoaderData<typeof loader>();
  
  return (
    <ul>
      {users.map((u) => (
        <li key={u.id}>{u.name}</li>
      ))}
    </ul>
  );
}
```

The `loader` is an HTTP endpoint, requiring all returned data to be JSON-serializable across the wire.

#### AirLib Providers
AirLib separates data resolution from view rendering. Attaching `.provide()` to the route resolves data during navigation before the page component renders:

```typescript
// pages/users/route.ts
export const usersRoute = route.provide('users', () => getUsers());
```

```tsx
// pages/users/page.tsx
import { For, page } from '@airlib/react';
import { usersRoute } from './route.js';

export default page(usersRoute).render(({ state }) => (
  <ul>
    <For each={() => state.data.users}>
      {({ name }) => <li>{name}</li>}
    </For>
  </ul>
));
```

The loader logic attaches directly to the route node, keeping the view component a pure, declarative UI layer.

### Pure Client-Side Rendering (CSR)

When data should be fetched from the browser after initial load, Remix uses `clientLoader`, while AirLib calls isomorphic functions directly within components.

#### Remix Client Loaders
In Remix, `clientLoader` fetches data in the browser during client navigation:

```tsx
// app/routes/users.tsx
import { useLoaderData } from "@remix-run/react";

export async function clientLoader() {
  const res = await fetch('/api/users');
  return res.json();
}
clientLoader.hydrate = true;

export function HydrateFallback() {
  return <div>Loading...</div>;
}

export default function UsersPage() {
  const users = useLoaderData<typeof clientLoader>();
  return (
    <ul>
      {users.map((u) => (
        <li key={u.id}>{u.name}</li>
      ))}
    </ul>
  );
}
```

#### AirLib Component
In AirLib, no special route-level client exports are needed. IRPC stubs provide reactive helpers like `.once()` directly inside components:

```tsx
// pages/users/page.tsx
import { For, Show, setup } from '@airlib/react';
import { getUsers } from './function.js';

export default setup(() => {
  const users = getUsers.once();

  return (
    <Show when={() => users.data} fallback={() => <div>Loading...</div>}>
      {(data) => (
        <ul>
          <For each={() => data}>
            {({ name }) => <li>{name}</li>}
          </For>
        </ul>
      )}
    </Show>
  );
});
```

The reactive reader returned by `.once()` automatically tracks loading state and unwraps resolved data without route fallback wrappers.

### Hybrid Rendering

To optimize perceived performance, applications often combine SSR for the static layout with CSR for slower data streams.

#### Remix Defer & Suspense
Remix streams HTML by returning a `defer()` response from the loader and wrapping delayed promises in `<Suspense>` and `<Await>`:

```tsx
// app/routes/dashboard.tsx
import { defer } from "@remix-run/node";
import { Await, useLoaderData } from "@remix-run/react";
import { Suspense } from "react";
import { db } from "../db.server";

export async function loader() {
  return defer({
    sales: db.sales.getSlowData(),
    analytics: db.analytics.getSlowData(),
  });
}

export default function DashboardPage() {
  const { sales, analytics } = useLoaderData<typeof loader>();

  return (
    <div className="grid">
      <Suspense fallback={<div className="skeleton">Loading sales...</div>}>
        <Await resolve={sales}>
          {(resolvedSales) => <div>{resolvedSales.total}</div>}
        </Await>
      </Suspense>

      <Suspense fallback={<div className="skeleton">Loading analytics...</div>}>
        <Await resolve={analytics}>
          {(resolvedAnalytics) => <div>{resolvedAnalytics.visitors}</div>}
        </Await>
      </Suspense>
    </div>
  );
}
```

#### AirLib Non-Blocking Fetching
In AirLib, pages and components are universal and render seamlessly on both server and browser. Moving data calls into component `.once()` invocations renders the shell instantly while data loads asynchronously.

```tsx
// pages/dashboard/page.tsx
import { Show, page } from '@airlib/react';
import { dashboardRoute } from './route.js';
import { getSalesData, getAnalyticsData } from './function.js';

export default page(dashboardRoute).render(() => {
  const sales = getSalesData.once();
  const analytics = getAnalyticsData.once();

  return (
    <div className="grid">
      <Show when={() => sales.data} fallback={() => <div className="skeleton">Loading sales...</div>}>
        {(data) => <div>{data.total}</div>}
      </Show>

      <Show when={() => analytics.data} fallback={() => <div className="skeleton">Loading analytics...</div>}>
        {(data) => <div>{data.visitors}</div>}
      </Show>
    </div>
  );
});
```

:::tip[Automatic Request Batching]
When multiple IRPC calls occur in the same execution tick, AirLib automatically batches them into a single streaming request. Each call streams and resolves independently without blocking other endpoints.
:::

## Mutations and Forms

When mutating data on the server, Remix relies on HTML `<form>` submissions with `FormData`, while AirLib uses direct isomorphic function calls with reactive form state.

### Remix Form Actions

Remix handles mutations using the standard HTML `<form>` element paired with an `action` function on the server:

```tsx
// app/routes/users.new.tsx
import { redirect } from "@remix-run/node";
import { Form, useNavigation } from "@remix-run/react";
import { db } from "../db.server";

export async function action({ request }: ActionFunctionArgs) {
  const formData = await request.formData();
  const name = formData.get("name") as string;
  
  await db.users.create({ name });
  return redirect("/users");
}

export default function NewUser() {
  const navigation = useNavigation();
  const isSubmitting = navigation.state === "submitting";

  return (
    <Form method="post">
      <input name="name" type="text" required />
      <button type="submit" disabled={isSubmitting}>
        {isSubmitting ? "Saving..." : "Create User"}
      </button>
    </Form>
  );
}
```

While embracing progressive enhancement, mutations are constrained to `FormData` serialization. Nested objects, numbers, and arrays require custom parsing or hidden field serialization.

### AirLib IRPC Form Call

In AirLib, calling an isomorphic remote function passes native typed JavaScript objects directly to the backend function:

```tsx
// pages/users/new/page.tsx
import { setup, render, mutable } from '@airlib/react';
import { createUser } from './function.js';

export default setup(() => {
  const form = mutable({ name: '' });
  const newUser = createUser.later();

  const submit = async (e: React.FormEvent<HTMLFormElement>) => {
    e.preventDefault();
    await newUser.dispatch(form.name);
  };

  return render(() => (
    <form onSubmit={submit}>
      <input 
        name="name" 
        value={form.name} 
        onInput={(e) => (form.name = e.currentTarget.value)} 
        required 
      />
      <button type="submit" disabled={newUser.status === 'pending'}>
        {newUser.status === 'pending' ? 'Saving...' : 'Create User'}
      </button>
    </form>
  ));
});
```

Because `createUser` is an isomorphic RPC stub, arguments maintain full end-to-end type safety without manual `FormData` unpacking.

## Client State Management

### Remix Client State

Remix encourages storing state in the URL search parameters or deriving it from the network. For local component state, standard React hooks are used:

```tsx
// app/components/counter.tsx
import { useState } from 'react';

export function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      Clicked {count} times
    </button>
  );
}
```

Sharing state across routes requires lifting state, URL Search Params, or external state management libraries.

### AirLib Reactive State

AirLib provides a built-in decoupled reactive state graph. Modifying reactive state triggers granular DOM updates without top-down component tree re-renders:

```tsx
// components/counter.tsx
import { setup, render, mutable } from '@airlib/react';

export const Counter = setup(() => {
  const state = mutable({ count: 0 });
  
  return render(() => (
    <button onClick={() => state.count++}>
      Clicked {state.count} times
    </button>
  ));
});
```

## Optimistic UI

### Remix Optimistic UI

Remix derives optimistic state by inspecting the pending `FormData` on `useFetcher`:

```tsx
// app/routes/posts.$id.tsx
import { useFetcher } from "@remix-run/react";

export function LikeButton({ post }: { post: { id: string; liked: boolean } }) {
  const fetcher = useFetcher();
  
  const isLiking = fetcher.formData?.get("intent") === "like";
  const optimisticLiked = isLiking ? true : post.liked;

  return (
    <fetcher.Form method="post" action={`/posts/${post.id}`}>
      <input type="hidden" name="intent" value={optimisticLiked ? "unlike" : "like"} />
      <button type="submit">
        {optimisticLiked ? 'Unlike' : 'Like'}
      </button>
    </fetcher.Form>
  );
}
```

### AirLib Reversible Mutations

AirLib provides the `undoable()` primitive. You apply the mutation directly to your reactive state, and `undoable` automatically records and reverts the exact mutation if the remote promise rejects:

```tsx
// components/like-button.tsx
import { setup, render, undoable } from '@airlib/react';
import { likePost } from './function.js';

export const LikeButton = setup<{ post: { id: string; liked: boolean } }>((props) => {
  const toggleLike = async () => {
    const [undo, settled] = undoable(() => {
      props.post.liked = !props.post.liked;
    });

    await likePost(props.post.id).then(settled, undo);
  };

  return render(() => (
    <button onClick={toggleLike}>
      {props.post.liked ? 'Unlike' : 'Like'}
    </button>
  ));
});
```

## Static Generation: SSG & On-Demand ISG

### Remix Static Workflow

Remix is primarily designed around dynamic server request execution and HTTP CDN caching (via `Cache-Control` headers). It lacks native granular on-demand static generation within the framework layer.

### AirLib SSG & On-Demand Pre-Rendering (ISG)

AirLib allows you to mark individual routes or entire route branches as `static` directly in their route definition:

```typescript
// pages/docs/route.ts (Build-time SSG)
export const docsRoute = route.config({ static: true });
```

During build, `airPages()` runs the worker against static routes and emits plain HTML into `dist/client/`. 

For dynamic paths (like `/blog/:slug`), AirLib provides **On-Demand Pre-Rendering (ISG)**:

```typescript
// pages/blog/route.ts (On-Demand ISG)
export const blogSlugRoute = slugRoute.config({ static: { maxAge: 3600 } });
```

On the first request to a new slug, the worker renders the page once and saves the static HTML to disk (or a custom `cacheAdapter` such as Cloudflare KV or Redis). Every subsequent request serves the static file instantly. When `maxAge` expires, the next request transparently refreshes the cached HTML in the background.

## Zero-JavaScript Delivery (Astro-like)

Content-centric websites (documentation, blogs, marketing pages) rarely need full client-side framework hydration on every page.

### Remix JS Footprint

Remix requires client hydration scripts (`<Scripts />`) to enable client-side navigation and form enhancements, shipping the React runtime on all pages.

### AirLib Zero-JavaScript Delivery

AirLib supports true zero-JavaScript delivery both **per-route** and **project-wide**:

#### Per-Route Zero-JavaScript
You can strip client JavaScript on specific content routes (e.g., landing, blog, or documentation pages) while keeping other application routes fully hydrated:

```typescript
// pages/about/route.ts
export const aboutRoute = route.config({ noscript: true });
```

#### Project-Wide Zero-JavaScript
For entirely static sites or documentation portals, enable `noscript` globally in your Vite configuration:

```typescript
// vite.config.ts
import { defineConfig } from 'vite';
import { airPages } from '@airlib/vite';

export default defineConfig({
  plugins: [
    airPages({
      noscript: true, // Ships pure static HTML/CSS with 0KB client JavaScript site-wide
    }),
  ],
});
```

When rendered, static pages are emitted as dehydrated HTML files with `<script>` tags completely stripped, achieving instant First Contentful Paint (FCP) and 100/100 Lighthouse performance.

## Extended Markdown & Content Authoring

### Remix MDX Workflow

In Remix, MDX requires configuring custom Vite rollup plugins or external MDX compilation pipelines with manual remark/rehype plugins.

### AirLib Extended MDX

AirLib includes built-in, zero-config Extended Markdown (`.page.mdx`). You simply create `.page.mdx` files inside `pages/`:

- **Frontmatter as Route Metadata** — YAML frontmatter automatically integrates with the route tree, navigation sidebar, and document `<Head>`.
- **Built-in Admonitions** — Native support for `:::note`, `:::tip`, `:::warning`, `:::danger`, and `:::details`.
- **Tabbed Code Groups** — Native `:::code-group` blocks for multi-language and multi-package manager examples.
- **Embedded JSX** — Embed live, interactive React or SolidJS components directly inside markdown without boilerplate wrapper files.

## Performance & Reactivity Footprint

### Deferred Hydration & Instant FCP

In traditional frameworks, client-side hydration scripts execute immediately when JavaScript chunks load, competing with the browser's main-thread rendering and layout passes.

In AirLib, **SSR always delivers 100% complete, fully styled HTML**. Because the user already sees the full visual state, AirLib **defers client hydration by default** (customizable per-route via `deferred`). This gives the browser time to paint the page instantly without main-thread jank, delivering instant First Contentful Paint (FCP) and near-zero Total Blocking Time (TBT).

| Performance Vector | Remix (React Router) | AirLib |
|---|---|---|
| **First Contentful Paint (FCP)** | Hydration scripts compete with initial render | Instant FCP (Complete SSR HTML + deferred hydration) |
| **Hydration Strategy** | Immediate synchronous client hydration | Non-blocking deferred hydration (configurable via `deferred`) |
| **Reactivity Model** | Virtual DOM reconciliation on component re-render | Fine-grained proxy mutations updating only touched DOM nodes |
| **Data Fetching Overhead** | Independent HTTP requests per loader | Automatic tick-based IRPC request batching & streaming |
| **Static Bundle Size** | Full React runtime on all routes | 0KB JavaScript static delivery option (`noscript`) |
| **Server Cold Starts** | Adapter initialization per platform | Lightweight universal worker runnable across Bun, Node, Deno, & Edge |

## Multi-Runtime Deployment

Remix uses separate server adapters (`@remix-run/node`, `@remix-run/cloudflare`, `@remix-run/express`) to deploy across targets.

AirLib builds a single **Universal SSR Worker** (`createApp`) that deploys identically across all major JavaScript runtimes with zero adapter overhead:

- **Bun** — `Bun.serve({ fetch: worker.fetch, websocket: worker.websocket })`
- **Node.js** — Native Hono/Node adapter
- **Deno** — `Deno.serve((req) => worker.fetch(req))`
- **Cloudflare Workers** — `export default { fetch: (req, env) => worker.fetch(req, env) }`

## Architectural Summary

| Dimension | Remix (React Router) | AirLib |
|---|---|---|
| **Routing** | Compiler-driven file-system routing | Assisted file-based routing |
| **State & Reactivity** | Immutable VDOM re-renders & React Context | Fine-grained reactive state |
| **Remote Functions** | HTTP Loaders & Form Actions (FormData) | Isomorphic remote functions & streams |
| **Component Model** | Route module boundaries | Universal components |
| **Form Handling** | FormData serialization & useNavigation | Direct reactive form state |
| **State Mutation** | Optimistic reducers & fetcher state | Direct reversible state mutations |
| **Hydration & FCP** | Immediate hydration competing with paint | Instant FCP & deferred hydration |
| **Static Generation** | HTTP CDN caching & export | Granular SSG & on-demand ISG |
| **Markdown / Content** | Custom Vite/MDX plugins | Built-in Extended MDX (`.page.mdx`) |
| **Static JS Footprint** | Ships full React runtime | Zero-JavaScript static delivery option |
| **SSR Engine** | Platform runtime adapters | Zero-adapter universal SSR worker |

## Final thoughts

Remix and AirLib solve full-stack web development through distinct engineering principles:

**Choose Remix if:** You prefer an architecture grounded in web standards, standard HTML `<form>` submissions, HTTP caching conventions, and React Router conventions.

**Choose AirLib if:** You want the productivity of assisted file-based routing combined with explicit typed route control, universal components, fine-grained reactive state, zero-JS static publishing, built-in MDX authoring, and native zero-adapter deployment across Bun, Node.js, Deno, and Cloudflare.

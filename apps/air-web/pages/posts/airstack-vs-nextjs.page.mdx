# AirLib vs. Next.js

:badge[Comparison]{variant="info"} :badge[Next.js]{variant="neutral"} :badge[App Router]{variant="neutral"} :badge[AirLib]{variant="neutral"}

<a href="https://nextjs.org/" target="_blank" rel="noreferrer">Next.js</a> is the dominant React framework, bringing React Server Components (RSC), Server Actions, and file-system routing to the mainstream. It dictates a strict architecture where the server drives the initial UI and client-side boundaries (`"use client"`) must be explicitly declared.

**AirLib** (Anchor, IRPC, Reactive) takes a different approach. It pairs **assisted file-based routing** with isomorphic remote functions and a decoupled reactive state graph. It treats the UI as an independent reactive layer where components render identically across server and client without fighting split `"use client"` / `"use server"` boundaries.

## Framework comparison

While both aim to deliver a seamless full-stack developer experience, their paradigm and developer workflows differ fundamentally.

| Aspect | Next.js App Router | AirLib |
|---|---|---|
| **Paradigm** | Server-Driven UI (Component-level server/client split) | Unified Reactive Model (Decoupled UI & logic) |
| **Routing** | Compiler-driven file-system routing | Assisted file-based routing (Explicit route graph) |
| **Data Fetching** | Server Components & React Suspense | Route Loaders & Isomorphic Remote Functions |
| **Mutations** | Server Actions & Cache Invalidation | Isomorphic Remote Functions & Reactive State |
| **State** | Immutable Component State | Fine-grained Reactive State |
| **Static Generation** | Build export & platform-tied ISR | Route-level SSG & On-Demand Pre-rendering (ISG) |
| **Content & Markdown** | Addon `@next/mdx` with plugin configuration | Built-in Extended MDX (`.page.mdx`) |
| **Static Delivery** | Always ships client React runtime | Pure Zero-JavaScript static HTML option |
| **Deployment** | Platform-specific runtime adapters | Zero-adapter Universal SSR Worker |

## Application Setup

Both frameworks offer file-based routing workflows, but they handle transparency and route control differently.

### Next.js Setup

In Next.js App Router, the file system dictates the application structure. You drop files into `app/` and the framework abstracts both client hydration and server execution behind its CLI and compiler virtual modules.

```tsx
// app/layout.tsx
export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>{children}</body>
    </html>
  );
}
```

```tsx
// app/page.tsx
export default function HomePage() {
  return (
    <main>
      <h1>Welcome to Next.js</h1>
    </main>
  );
}
```

Next.js implicitly handles React root hydration (`createRoot`), router configuration, and request handling. While dropping files is effortless, routing internals and tree mutations remain locked inside opaque framework compiler abstractions.

### AirLib Setup

AirLib bridges file-system simplicity with explicit, typed route orchestration through **assisted file-based routing**:

- **Drop-and-Go Pages** — Dropping a `page.tsx` or `layout.tsx` into `pages/` automatically establishes the route definition with typed exports and starter boilerplate.
- **Zero Black Boxes** — Routes are not opaque virtual modules hidden inside the compiler. The route definition lives directly in your project as plain TypeScript.
- **Full Programmatic Power** — Having an explicit route definition alongside your component gives you full control to attach access guards (`.guard()`), asynchronous data loaders (`.provide()`), and route metadata with full IDE autocomplete.

```tsx
// pages/layout.tsx
import { page } from '@airlib/react';
import { rootRoute } from './route.js';

export default page(rootRoute).render(({ children }) => (
  <div className="app">
    <header>My App</header>
    {children}
  </div>
));
```

```tsx
// pages/page.tsx
import { page } from '@airlib/react';
import { rootIndexRoute } from './route.js';

export default page(rootIndexRoute).render(() => (
  <main>
    <h1>Welcome to AirLib</h1>
  </main>
));
```

The accompanying `route.ts` maintains the typed route graph:

```typescript
// pages/route.ts
import router from '@/src/router.js';

/** AirLib managed */
const route = router.route();
const indexRoute = route.route('/');
/** AirLib managed */

export const rootRoute = route;
export const rootIndexRoute = indexRoute;

export default rootRoute;
```

You get the convenience of file-system routing without sacrificing explicit typed control over route lifecycles and middleware.

## Rendering Paradigms

Modern applications require different rendering strategies depending on the data. Both frameworks support Server-Side Rendering (SSR), Client-Side Rendering (CSR), and Hybrid approaches, but they use completely different mechanisms to achieve them.

### Pure Server-Side Rendering (SSR)
To fetch data on the server and render static HTML without client-side JavaScript fetching overhead, Next.js uses Server Components, while AirLib uses route-level providers.

#### Next.js Server Components
Next.js achieves this via Server Components. The server halts, waits for the database, and sends the finished HTML.

```tsx
// app/users/page.tsx
import { db } from '@/lib/db';

export default async function UsersPage() {
  const users = await db.users.findMany();
  return (
    <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>
  );
}
```

This tightly couples the backend query directly into the component definition, preventing the component from functioning as a standalone client UI element.

#### AirLib Providers
AirLib separates data resolution from view rendering. Attaching `.provide()` to the route resolves data during navigation before the page component renders.

```typescript
// pages/users/route.ts
export const usersRoute = route.provide('users', () => getUsers());
```

```tsx
// pages/users/page.tsx
import { For, page } from '@airlib/react';
import { usersRoute } from './route.js';

export default page(usersRoute).render(({ state }) => (
  <ul>
    <For each={() => state.data.users}>
      {({ name }) => <li>{name}</li>}
    </For>
  </ul>
));
```

The component stays pure and synchronous, receiving strongly typed data directly from `state.data`.

### Pure Client-Side Rendering (CSR)
To fetch data in the browser after the initial shell loads, Next.js requires explicit client boundaries, while AirLib calls isomorphic remote functions directly inside components.

#### Next.js Client Components
In Next.js, you must explicitly opt out of Server Components with `"use client"` and manage lifecycle hooks manually.

```tsx
// app/users/page.tsx
'use client'
import { useState, useEffect } from 'react';

export default function UsersPage() {
  const [users, setUsers] = useState(null);
  
  useEffect(() => {
    fetch('/api/users').then(res => res.json()).then(setUsers);
  }, []);

  if (!users) return <div>Loading...</div>;
  return <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>;
}
```

The component manually coordinates effects, unmounting state, and network race conditions.

#### AirLib Component
In AirLib, no `"use client"` directive or `useEffect` boilerplate is needed. IRPC stubs provide reactive execution helpers like `.once()` directly:

```tsx
// pages/users/page.tsx
import { For, Show, setup } from '@airlib/react';
import { getUsers } from './function.js';

export default setup(() => {
  const users = getUsers.once();

  return (
    <Show when={() => users.data} fallback={() => <div>Loading...</div>}>
      {(data) => (
        <ul>
          <For each={() => data}>
            {({ name }) => <li>{name}</li>}
          </For>
        </ul>
      )}
    </Show>
  );
});
```

The reactive reader returned by `.once()` tracks loading state and unwraps data automatically.

### Hybrid Rendering
To optimize perceived performance, applications often combine SSR for the static layout with CSR for heavy, slow data. Next.js relies on server-side HTTP streaming, while AirLib uses non-blocking reactive component calls.

#### Next.js Streaming & Suspense
Next.js streams HTML by sending layout chunks immediately while holding `<Suspense>` boundaries open until server promises resolve:

```tsx
// app/dashboard/layout.tsx
export default function DashboardLayout({ children }: { children: React.ReactNode }) {
  return (
    <div>
      <header>Static Header</header>
      {children}
    </div>
  );
}
```

```tsx
// app/dashboard/page.tsx
import { Suspense } from 'react';
import { db } from '@/lib/db';

async function SalesWidget() {
  const data = await db.sales.getSlowData();
  return <div>{data.total}</div>;
}

async function AnalyticsWidget() {
  const data = await db.analytics.getSlowData();
  return <div>{data.visitors}</div>;
}

export default function DashboardPage() {
  return (
    <div className="grid">
      <Suspense fallback={<div className="skeleton">Loading sales...</div>}>
        <SalesWidget />
      </Suspense>
      
      <Suspense fallback={<div className="skeleton">Loading analytics...</div>}>
        <AnalyticsWidget />
      </Suspense>
    </div>
  );
}
```

#### AirLib Non-Blocking Fetching
In AirLib, pages and components are universal and render seamlessly on both server and browser. Moving data calls into component `.once()` invocations renders the shell instantly while data loads asynchronously.

```tsx
// pages/dashboard/page.tsx
import { Show, page } from '@airlib/react';
import { dashboardRoute } from './route.js';
import { getSalesData, getAnalyticsData } from './function.js';

export default page(dashboardRoute).render(() => {
  const sales = getSalesData.once();
  const analytics = getAnalyticsData.once();

  return (
    <div className="grid">
      <Show when={() => sales.data} fallback={() => <div className="skeleton">Loading sales...</div>}>
        {(data) => <div>{data.total}</div>}
      </Show>

      <Show when={() => analytics.data} fallback={() => <div className="skeleton">Loading analytics...</div>}>
        {(data) => <div>{data.visitors}</div>}
      </Show>
    </div>
  );
});
```

:::tip[Automatic Request Batching]
When multiple IRPC procedures execute on the same tick (like `sales` and `analytics`), IRPC automatically batches them into a single transport request, streaming individual responses back as they resolve.
:::

## Mutations and Forms

Sending data back to the server is traditionally done via API routes. Next.js introduced Server Actions to bridge this gap, while AirLib uses isomorphic remote functions and reactive bindings.

### Next.js Server Actions

Server Actions allow you to define asynchronous server functions called from client components or form actions. Managing submission state requires `useFormStatus` inside a dedicated child component, and the server cache must be manually invalidated with `revalidatePath`.

```tsx
// app/actions.ts
'use server'

import { db } from '@/lib/db';
import { revalidatePath } from 'next/cache';

export async function createUser(formData: FormData) {
  const name = formData.get('name') as string;
  await db.users.create({ name });
  
  // Explicitly invalidate server cache
  revalidatePath('/users');
}
```

```tsx
// app/users/new/page.tsx
'use client'

import { useFormStatus } from 'react-dom';
import { createUser } from '../../actions';

function SubmitButton() {
  const { pending } = useFormStatus();
  return <button type="submit" disabled={pending}>Create User</button>;
}

export default function NewUserForm() {
  return (
    <form action={createUser}>
      <input name="name" required />
      <SubmitButton />
    </form>
  );
}
```

### AirLib IRPC Call

AirLib mutations are standard TypeScript functions called through IRPC stubs. Component forms bind directly to mutable state and track asynchronous dispatch lifecycles with `.later()`:

```tsx
// pages/users/new/page.tsx
import { setup, render, mutable } from '@airlib/react';
import { createUser } from './function.js';

export default setup(() => {
  const form = mutable({ name: '' });
  const newUser = createUser.later();

  const submit = async (e: React.FormEvent<HTMLFormElement>) => {
    e.preventDefault();
    await newUser.dispatch(form.name);
  };

  return render(() => (
    <form onSubmit={submit}>
      <input 
        name="name" 
        value={form.name} 
        onInput={(e) => (form.name = e.currentTarget.value)} 
        required 
      />
      <button type="submit" disabled={newUser.status === 'pending'}>Create User</button>
    </form>
  ));
});
```

Because state mutations are fine-grained and reactive, changes update the UI immediately without requiring cache invalidation tags or `revalidatePath` calls.

## Client State Management

When your app needs interactive local state, the two frameworks use different reactivity primitives.

### Next.js Client State

In Next.js, interactive state requires adding `"use client"` and using standard React hooks and immutable update patterns:

```tsx
// app/components/counter.tsx
'use client'

import { useState } from 'react';

export function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      Clicked {count} times
    </button>
  );
}
``` 

### AirLib State

In AirLib, state is universal and fine-grained reactive. There are no `"use client"` directives or artificial boundary rules:

```tsx
// components/counter.tsx
import { setup, render, mutable } from '@airlib/react';

export const Counter = setup(() => {
  const state = mutable({ count: 0 });
  
  return render(() => (
    <button onClick={() => state.count++}>
      Clicked {state.count} times
    </button>
  ));
});
```

## Optimistic UI

Both frameworks provide primitives to instantly update the UI before the server responds.

### Next.js Optimistic UI

Next.js provides `useOptimistic`, requiring a base server state, a reducer, and a React Transition wrapper:

```tsx
'use client'
import { useOptimistic, startTransition } from 'react';
import { likePost } from './actions';

export function LikeButton({ post }: { post: { id: string; liked: boolean } }) {
  const [optimisticLike, addOptimisticLike] = useOptimistic(
    post.liked,
    (state, newLike: boolean) => newLike
  );

  const toggleLike = () => {
    startTransition(async () => {
      addOptimisticLike(!post.liked);
      await likePost(post.id);
    });
  };

  return (
    <button onClick={toggleLike}>
      {optimisticLike ? 'Unlike' : 'Like'}
    </button>
  );
}
```

### AirLib Reversible Mutations

AirLib provides the `undoable()` primitive. You apply the mutation directly to your reactive state, and `undoable` automatically records and reverts the exact mutation if the remote promise rejects:

```tsx
// components/like-button.tsx
import { setup, render, undoable } from '@airlib/react';
import { likePost } from './function.js';

export const LikeButton = setup<{ post: { id: string; liked: boolean } }>((props) => {
  const toggleLike = async () => {
    const [undo, settled] = undoable(() => {
      props.post.liked = !props.post.liked;
    });

    await likePost(props.post.id).then(settled, undo);
  };

  return render(() => (
    <button onClick={toggleLike}>
      {props.post.liked ? 'Unlike' : 'Like'}
    </button>
  ));
});
```

## Static Generation: SSG & On-Demand ISG

Pre-rendering pages ahead of time reduces database load and delivers instant responses from edge CDNs or disk storage.

### Next.js SSG & ISR

In Next.js, static routes are configured via `generateStaticParams()` and runtime revalidation flags (`revalidate = 3600`). Revalidation (ISR) is tightly coupled to Node.js server processes or Vercel's proprietary edge cache infrastructure.

```tsx
// app/blog/[slug]/page.tsx
export async function generateStaticParams() {
  const posts = await db.posts.findMany();
  return posts.map((p) => ({ slug: p.slug }));
}

export const revalidate = 3600; // Revalidate every hour
```

### AirLib SSG & On-Demand Pre-Rendering (ISG)

AirLib allows you to mark individual routes or entire route branches as `static` directly in their route definition:

```typescript
// pages/docs/route.ts (Build-time SSG)
export const docsRoute = route.config({ static: true });
```

During build, `airPages()` runs the worker against static routes and emits plain HTML into `dist/client/`. 

For dynamic paths (like `/blog/:slug`), AirLib provides **On-Demand Pre-Rendering (ISG)**:

```typescript
// pages/blog/route.ts (On-Demand ISG)
export const blogSlugRoute = slugRoute.config({ static: { maxAge: 3600 } });
```

On the first request to a new slug, the worker renders the page once and saves the static HTML to disk (or a custom `cacheAdapter` such as Cloudflare KV or Redis). Every subsequent request serves the static file instantly. When `maxAge` expires, the next request transparently refreshes the cached HTML in the background.

## Zero-JavaScript Delivery (Astro-like)

Content-centric websites (documentation, blogs, marketing pages) rarely need full client-side framework hydration on every page.

### Next.js JS Footprint

Next.js always ships the React runtime, framework scheduler, client router, and component hydration bundles to the browser (typically 80KB–100KB+ minimum baseline JavaScript), even for completely static content. There is no official configuration to strip client JavaScript while preserving full SSR components.

### AirLib Zero-JavaScript Delivery

AirLib supports true zero-JavaScript delivery both **per-route** and **project-wide**:

#### Per-Route Zero-JavaScript
You can strip client JavaScript on specific content routes (e.g., landing, blog, or documentation pages) while keeping other application routes fully hydrated:

```typescript
// pages/about/route.ts
export const aboutRoute = route.config({ noscript: true });
```

#### Project-Wide Zero-JavaScript
For entirely static sites or documentation portals, enable `noscript` globally in your Vite configuration:

```typescript
// vite.config.ts
import { defineConfig } from 'vite';
import { airPages } from '@airlib/vite';

export default defineConfig({
  plugins: [
    airPages({
      noscript: true, // Ships pure static HTML/CSS with 0KB client JavaScript site-wide
    }),
  ],
});
```

When rendered, static pages are emitted as dehydrated HTML files with `<script>` tags completely stripped. Like Astro, your pages achieve instant First Contentful Paint (FCP), zero hydration lag, and 100/100 Lighthouse performance, while retaining full authoring in React/Solid JSX or MDX.

## Extended Markdown & Content Authoring

Documentation and content-driven sites require rich formatting like admonitions, tabbed code snippets, and embedded live components.

### Next.js MDX Workflow

In Next.js, adding MDX requires configuring `@next/mdx`, adjusting `next.config.js`, managing compiler loaders, and manually installing remark/rehype plugins for callouts and code blocks.

### AirLib Extended MDX

AirLib includes built-in, zero-config Extended Markdown (`.page.mdx`). You simply create `.page.mdx` files inside `pages/`:

- **Frontmatter as Route Metadata** — YAML frontmatter automatically integrates with the route tree, navigation sidebar, and document `<Head>`.
- **Built-in Admonitions** — Native support for `:::note`, `:::tip`, `:::warning`, `:::danger`, and `:::details`.
- **Tabbed Code Groups** — Native `:::code-group` blocks for multi-language and multi-package manager examples.
- **Embedded JSX** — Embed live, interactive React or SolidJS components directly inside markdown without boilerplate wrapper files.

## Performance & Reactivity Footprint

### Deferred Hydration & Instant FCP

In Next.js, client-side hydration scripts execute immediately when JavaScript chunks load, competing with the browser's main-thread rendering and layout passes.

In AirLib, **SSR always delivers 100% complete, fully styled HTML**. Because the user already sees the full visual state, AirLib **defers client hydration by default** (customizable per-route via `deferred`). This gives the browser time to paint the page instantly without main-thread jank, delivering instant First Contentful Paint (FCP) and near-zero Total Blocking Time (TBT) even on complex interactive pages.

| Performance Vector | Next.js App Router | AirLib |
|---|---|---|
| **First Contentful Paint (FCP)** | Hydration scripts compete with initial render | Instant FCP (Complete SSR HTML + deferred hydration) |
| **Hydration Strategy** | Immediate synchronous client hydration | Non-blocking deferred hydration (configurable via `deferred`) |
| **Reactivity Model** | Virtual DOM reconciliation on component re-render | Fine-grained proxy mutations updating only touched DOM nodes |
| **Data Fetching Overhead** | Individual `fetch()` calls or manual parallel Promise arrays | Automatic tick-based IRPC request batching & streaming |
| **Static Bundle Size** | ~80KB+ React runtime minimum on static pages | 0KB JavaScript static delivery option (`noscript`) |
| **Server Cold Starts** | Heavy Node.js runtime initialization | Lightweight universal worker runnable across Bun, Node, Deno, & Edge |

## Multi-Runtime Deployment

Next.js is tightly coupled to Node.js / Vercel Edge runtimes with proprietary adapter layers.

AirLib builds a single **Universal SSR Worker** (`createApp`) that deploys identically across all major JavaScript runtimes with zero adapter overhead:

- **Bun** — `Bun.serve({ fetch: worker.fetch, websocket: worker.websocket })`
- **Node.js** — Native Hono/Node adapter
- **Deno** — `Deno.serve((req) => worker.fetch(req))`
- **Cloudflare Workers** — `export default { fetch: (req, env) => worker.fetch(req, env) }`

| Dimension | Next.js App Router | AirLib |
|---|---|---|
| **Routing** | Compiler-driven file-system routing | Assisted file-based routing |
| **State & Reactivity** | Immutable VDOM re-renders & React Transitions | Fine-grained reactive state |
| **Remote Functions** | Server Actions & Cache Invalidation | Isomorphic remote functions & streams |
| **Component Model** | Split Client and Server Boundaries | Universal components |
| **Form Handling** | Action state & separate status consumers | Direct reactive form state |
| **State Mutation** | Optimistic reducers & transitions | Direct reversible state mutations |
| **Hydration & FCP** | Immediate hydration competing with paint | Instant FCP & deferred hydration |
| **Static Generation** | Build export & platform-tied ISR | Granular SSG & on-demand ISG |

| **Static JS Footprint** | Ships full React runtime | Zero-JavaScript static delivery option |
| **SSR Engine** | Platform runtime adapters | Zero-adapter universal SSR worker |

## Final thoughts

Next.js and AirLib take fundamentally different approaches to full-stack application development:

**Choose Next.js if:** You prefer an opinionated ecosystem built heavily around React Server Components, server-driven component boundaries, and Vercel infrastructure conventions.

**Choose AirLib if:** You want the productivity of file-based routing combined with explicit typed route control, universal components without `"use client"` splits, fine-grained reactive state, zero-JS static publishing, built-in MDX authoring, and native zero-adapter deployment across Bun, Node.js, Deno, and Cloudflare.

# AirLib vs. TanStack

:badge[Comparison]{variant="info"} :badge[TanStack]{variant="neutral"} :badge[Router]{variant="neutral"} :badge[AirLib]{variant="neutral"}

<a href="https://tanstack.com/" target="_blank" rel="noreferrer">TanStack</a> is a collection of high-quality, headless utilities. To build a full-stack React application, developers typically assemble **TanStack Router** (for type-safe routing) and **TanStack Query** (for data fetching and caching), manually connecting them to backend APIs (such as tRPC or REST).

**AirLib** (Anchor, IRPC, Reactive) takes a unified approach. Rather than assembling disparate libraries to handle routing, fetching, caching, and state, it provides a cohesive ecosystem. The router and data fetching layer share the same reactive state graph, eliminating the need for separate query caches, manual cache invalidation, or network boilerplate.

## Framework comparison

While both aim to deliver highly interactive, type-safe full-stack applications, their approaches to architecture, composition, and state management differ fundamentally.

| Aspect | TanStack (Router + Query) | AirLib |
|---|---|---|
| **Paradigm** | Assembled Modular Libraries | Unified Reactive Model (Decoupled UI & logic) |
| **Routing** | Code/file-based routing with CLI codegen | Assisted file-based routing (Explicit route graph) |
| **Data Fetching** | Query Client & manual cache invalidation | Route Loaders & Isomorphic Remote Functions |
| **Mutations** | useMutation & manual cache rollbacks | Isomorphic Remote Functions & Reactive State |
| **State** | Query Cache & React useState/Context | Fine-grained Reactive State |
| **Static Generation** | Build export or custom server setups | Granular SSG & On-Demand ISG |
| **Content & Markdown** | Manual markdown loaders & plugins | Built-in Extended MDX (`.page.mdx`) |
| **Static Delivery** | Always ships client React runtime | Pure Zero-JavaScript static HTML option |
| **Deployment** | Client SPA host or custom runtime | Zero-adapter Universal SSR Worker |

## Application Setup

Both frameworks operate across client and server environments, but they manage transparency and route orchestration differently.

### TanStack Setup

In TanStack Router, you define a root layout route (`__root.tsx`) and page routes (`index.tsx`), generating a virtual route tree via CLI:

```tsx
// src/routes/__root.tsx
import { createRootRoute, Outlet } from '@tanstack/react-router';

export const Route = createRootRoute({
  component: () => (
    <div className="app">
      <header>My App</header>
      <Outlet />
    </div>
  ),
});
```

```tsx
// src/routes/index.tsx
import { createFileRoute } from '@tanstack/react-router';

export const Route = createFileRoute('/')({
  component: () => (
    <main>
      <h1>Welcome to TanStack</h1>
    </main>
  ),
});
```

You then assemble the router and wrap the application in multiple context providers:

```tsx
// src/main.tsx
import { createRouter, RouterProvider } from '@tanstack/react-router';
import { QueryClient, QueryClientProvider } from '@tanstack/react-query';
import { routeTree } from './routeTree.gen';

const queryClient = new QueryClient();
const router = createRouter({ routeTree, context: { queryClient } });

export function App() {
  return (
    <QueryClientProvider client={queryClient}>
      <RouterProvider router={router} />
    </QueryClientProvider>
  );
}
```

### AirLib Setup

AirLib unifies the router and the reactivity graph through **assisted file-based routing**:

- **Drop-and-Go Pages** — Dropping a `page.tsx` or `layout.tsx` into `pages/` automatically establishes the route definition with typed exports and starter boilerplate.
- **Zero Black Boxes** — Routes are not opaque virtual modules hidden inside the compiler. The route definition lives directly in your project as plain TypeScript.
- **Full Programmatic Power** — Having an explicit route definition alongside your component gives you full control to attach access guards (`.guard()`), asynchronous data loaders (`.provide()`), and route metadata with full IDE autocomplete.

```tsx
// pages/layout.tsx
import { page } from '@airlib/react';
import { rootRoute } from './route.js';

export default page(rootRoute).render(({ children }) => (
  <div className="app">
    <header>My App</header>
    {children}
  </div>
));
```

```tsx
// pages/page.tsx
import { page } from '@airlib/react';
import { rootIndexRoute } from './route.js';

export default page(rootIndexRoute).render(() => (
  <main>
    <h1>Welcome to AirLib</h1>
  </main>
));
```

The accompanying `route.ts` maintains the typed route graph:

```typescript
// pages/route.ts
import router from '@/src/router.js';

/** AirLib managed */
const route = router.route();
const indexRoute = route.route('/');
/** AirLib managed */

export const rootRoute = route;
export const rootIndexRoute = indexRoute;

export default rootRoute;
```

## Rendering Paradigms

Both TanStack and AirLib support full-stack rendering, but they differ in how they hydrate the client, orchestrate loaders, and manage asynchronous data.

### Server-Side Rendering (SSR)

To fetch data on the server and render HTML before sending it to the client, TanStack coordinates router loaders with the query cache, while AirLib uses route data providers.

#### TanStack SSR
In TanStack Router, you define a `loader` that runs before the route renders. When paired with TanStack Query, you use `queryClient.ensureQueryData` to populate the server cache, which is then dehydrated to the client:

```tsx
import { createFileRoute } from '@tanstack/react-router';
import { queryOptions, useSuspenseQuery } from '@tanstack/react-query';

const usersQuery = queryOptions({
  queryKey: ['users'],
  queryFn: () => fetch('/api/users').then((r) => r.json()),
});

export const Route = createFileRoute('/users')({
  loader: ({ context: { queryClient } }) => queryClient.ensureQueryData(usersQuery),
  component: UsersPage,
});

function UsersPage() {
  const { data } = useSuspenseQuery(usersQuery);

  return (
    <ul>
      {data.map((u) => (
        <li key={u.id}>{u.name}</li>
      ))}
    </ul>
  );
}
```

#### AirLib Providers
AirLib separates data resolution from view rendering. Attaching `.provide()` to the route resolves data during navigation before the page component renders:

```typescript
// pages/users/route.ts
export const usersRoute = route.provide('users', () => getUsers());
```

```tsx
// pages/users/page.tsx
import { For, page } from '@airlib/react';
import { usersRoute } from './route.js';

export default page(usersRoute).render(({ state }) => (
  <ul>
    <For each={() => state.data.users}>
      {({ name }) => <li>{name}</li>}
    </For>
  </ul>
));
```

The loader logic attaches directly to the route node, keeping the view component a pure, declarative UI layer without external cache dehydration.

### Pure Client-Side Rendering (CSR)

When data should be fetched from the browser after initial load, TanStack uses `useQuery`, while AirLib calls isomorphic functions directly within components.

#### TanStack Client Query
In TanStack, you use the `useQuery` hook inside the component for client-side fetching:

```tsx
import { useQuery } from '@tanstack/react-query';

export function UsersPage() {
  const { data, isLoading } = useQuery(usersQuery);

  if (isLoading) return <div>Loading...</div>;

  return (
    <ul>
      {data.map((u) => (
        <li key={u.id}>{u.name}</li>
      ))}
    </ul>
  );
}
```

#### AirLib Component
In AirLib, IRPC stubs provide reactive helpers like `.once()` directly inside components:

```tsx
// pages/users/page.tsx
import { For, Show, setup } from '@airlib/react';
import { getUsers } from './function.js';

export default setup(() => {
  const users = getUsers.once();

  return (
    <Show when={() => users.data} fallback={() => <div>Loading...</div>}>
      {(data) => (
        <ul>
          <For each={() => data}>
            {({ name }) => <li>{name}</li>}
          </For>
        </ul>
      )}
    </Show>
  );
});
```

The reactive reader returned by `.once()` automatically tracks loading state and unwraps resolved data without manual cache key orchestration.

### Hybrid Rendering

To optimize perceived performance, applications often combine SSR for the static layout with CSR for slower data streams.

#### TanStack Defer & Suspense
In TanStack Router, you return a deferred promise from your loader, wrapping delayed promises in `<Suspense>` and `<Await>`:

```tsx
import { defer, Await, createFileRoute } from '@tanstack/react-router';
import { Suspense } from 'react';

export const Route = createFileRoute('/dashboard')({
  loader: () => ({
    sales: defer(fetch('/api/sales').then((r) => r.json())),
    analytics: defer(fetch('/api/analytics').then((r) => r.json())),
  }),
  component: DashboardPage,
});

function DashboardPage() {
  const { sales, analytics } = Route.useLoaderData();

  return (
    <div className="grid">
      <Suspense fallback={<div className="skeleton">Loading sales...</div>}>
        <Await promise={sales}>
          {(data) => <div>{data.total}</div>}
        </Await>
      </Suspense>

      <Suspense fallback={<div className="skeleton">Loading analytics...</div>}>
        <Await promise={analytics}>
          {(data) => <div>{data.visitors}</div>}
        </Await>
      </Suspense>
    </div>
  );
}
```

#### AirLib Non-Blocking Fetching
In AirLib, pages and components are universal and render seamlessly on both server and browser. Moving data calls into component `.once()` invocations renders the shell instantly while data loads asynchronously.

```tsx
// pages/dashboard/page.tsx
import { Show, page } from '@airlib/react';
import { dashboardRoute } from './route.js';
import { getSalesData, getAnalyticsData } from './function.js';

export default page(dashboardRoute).render(() => {
  const sales = getSalesData.once();
  const analytics = getAnalyticsData.once();

  return (
    <div className="grid">
      <Show when={() => sales.data} fallback={() => <div className="skeleton">Loading sales...</div>}>
        {(data) => <div>{data.total}</div>}
      </Show>

      <Show when={() => analytics.data} fallback={() => <div className="skeleton">Loading analytics...</div>}>
        {(data) => <div>{data.visitors}</div>}
      </Show>
    </div>
  );
});
```

:::tip[Automatic Request Batching]
When multiple IRPC calls occur in the same execution tick, AirLib automatically batches them into a single streaming request. Each call streams and resolves independently without blocking other endpoints.
:::

## Mutations and Forms

When sending data to the server, TanStack Query provides `useMutation` requiring manual cache key invalidation, while AirLib relies on direct isomorphic function calls with reactive form state.

### TanStack Mutations

TanStack handles mutations via the `useMutation` hook. Because data is cached under arbitrary query keys, you must manually invalidate matching queries to keep the UI synchronized:

```tsx
// components/new-user.tsx
import { useMutation, useQueryClient } from '@tanstack/react-query';
import { useState } from 'react';

export function NewUserForm() {
  const queryClient = useQueryClient();
  const [name, setName] = useState("");

  const mutation = useMutation({
    mutationFn: (newName: string) => fetch('/api/users', { 
      method: 'POST', body: JSON.stringify({ name: newName }) 
    }),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['users'] });
    },
  });

  return (
    <form onSubmit={(e) => {
      e.preventDefault();
      mutation.mutate(name);
    }}>
      <input value={name} onChange={(e) => setName(e.target.value)} required />
      <button type="submit" disabled={mutation.isPending}>
        {mutation.isPending ? 'Saving...' : 'Create User'}
      </button>
    </form>
  );
}
```

The disconnect between mutation responses and cached query trees requires manual orchestration via the `QueryClient`.

### AirLib IRPC Form Call

In AirLib, calling an isomorphic remote function passes native typed JavaScript objects directly to the backend function:

```tsx
// pages/users/new/page.tsx
import { setup, render, mutable } from '@airlib/react';
import { createUser } from './function.js';

export default setup(() => {
  const form = mutable({ name: '' });
  const newUser = createUser.later();

  const submit = async (e: React.FormEvent<HTMLFormElement>) => {
    e.preventDefault();
    await newUser.dispatch(form.name);
  };

  return render(() => (
    <form onSubmit={submit}>
      <input 
        name="name" 
        value={form.name} 
        onInput={(e) => (form.name = e.currentTarget.value)} 
        required 
      />
      <button type="submit" disabled={newUser.status === 'pending'}>
        {newUser.status === 'pending' ? 'Saving...' : 'Create User'}
      </button>
    </form>
  ));
});
```

Because `createUser` is an isomorphic RPC stub, arguments maintain full end-to-end type safety without manual cache invalidation boilerplate.

## Client State Management

### TanStack State

In TanStack, server state lives in the Query Cache, while local UI state is managed via React hooks (`useState`, `useReducer`) or external libraries (Zustand, Redux):

```tsx
// components/counter.tsx
import { useState } from 'react';

export function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      Clicked {count} times
    </button>
  );
}
```

This creates a duality where developers must decide whether state belongs in the server cache or local client stores.

### AirLib Reactive State

AirLib provides a built-in decoupled reactive state graph. Modifying reactive state triggers granular DOM updates without top-down component tree re-renders:

```tsx
// components/counter.tsx
import { setup, render, mutable } from '@airlib/react';

export const Counter = setup(() => {
  const state = mutable({ count: 0 });
  
  return render(() => (
    <button onClick={() => state.count++}>
      Clicked {state.count} times
    </button>
  ));
});
```

## Optimistic UI

### TanStack Optimistic Cache

In TanStack Query, you achieve optimistic UI by hooking into the `onMutate` callback. You must manually cancel inflight queries, snapshot previous cache state, mutate the cache synchronously, and handle error rollbacks:

```tsx
// components/like-button.tsx
import { useMutation, useQueryClient } from '@tanstack/react-query';

export function LikeButton({ post }: { post: { id: string; liked: boolean } }) {
  const queryClient = useQueryClient();

  const mutation = useMutation({
    mutationFn: (id: string) => fetch(`/api/posts/${id}/like`, { method: 'POST' }),
    onMutate: async (id) => {
      await queryClient.cancelQueries({ queryKey: ['posts', id] });
      const previousPost = queryClient.getQueryData(['posts', id]);
      
      queryClient.setQueryData(['posts', id], (old: any) => ({
        ...old,
        liked: !old.liked,
      }));
      
      return { previousPost };
    },
    onError: (err, id, context) => {
      queryClient.setQueryData(['posts', id], context?.previousPost);
    },
  });

  return (
    <button onClick={() => mutation.mutate(post.id)}>
      {post.liked ? 'Unlike' : 'Like'}
    </button>
  );
}
```

### AirLib Reversible Mutations

AirLib provides the `undoable()` primitive. You apply the mutation directly to your reactive state, and `undoable` automatically records and reverts the exact mutation if the remote promise rejects:

```tsx
// components/like-button.tsx
import { setup, render, undoable } from '@airlib/react';
import { likePost } from './function.js';

export const LikeButton = setup<{ post: { id: string; liked: boolean } }>((props) => {
  const toggleLike = async () => {
    const [undo, settled] = undoable(() => {
      props.post.liked = !props.post.liked;
    });

    await likePost(props.post.id).then(settled, undo);
  };

  return render(() => (
    <button onClick={toggleLike}>
      {props.post.liked ? 'Unlike' : 'Like'}
    </button>
  ));
});
```

## Static Generation: SSG & On-Demand ISG

### TanStack Static Workflow

TanStack Router can be exported statically for SPA hosting or wired into custom SSR server pipelines, but it lacks native route-level incremental static generation (ISG) and cache tiering out of the box.

### AirLib SSG & On-Demand Pre-Rendering (ISG)

AirLib allows you to mark individual routes or entire route branches as `static` directly in their route definition:

```typescript
// pages/docs/route.ts (Build-time SSG)
export const docsRoute = route.config({ static: true });
```

During build, `airPages()` runs the worker against static routes and emits plain HTML into `dist/client/`. 

For dynamic paths (like `/blog/:slug`), AirLib provides **On-Demand Pre-Rendering (ISG)**:

```typescript
// pages/blog/route.ts (On-Demand ISG)
export const blogSlugRoute = slugRoute.config({ static: { maxAge: 3600 } });
```

On the first request to a new slug, the worker renders the page once and saves the static HTML to disk (or a custom `cacheAdapter` such as Cloudflare KV or Redis). Every subsequent request serves the static file instantly. When `maxAge` expires, the next request transparently refreshes the cached HTML in the background.

## Zero-JavaScript Delivery (Astro-like)

Content-centric websites (documentation, blogs, marketing pages) rarely need full client-side framework hydration on every page.

### TanStack JS Footprint

TanStack requires client hydration scripts to initialize Router and Query stores, shipping the full React runtime and state machinery on all pages.

### AirLib Zero-JavaScript Delivery

AirLib supports true zero-JavaScript delivery both **per-route** and **project-wide**:

#### Per-Route Zero-JavaScript
You can strip client JavaScript on specific content routes (e.g., landing, blog, or documentation pages) while keeping other application routes fully hydrated:

```typescript
// pages/about/route.ts
export const aboutRoute = route.config({ noscript: true });
```

#### Project-Wide Zero-JavaScript
For entirely static sites or documentation portals, enable `noscript` globally in your Vite configuration:

```typescript
// vite.config.ts
import { defineConfig } from 'vite';
import { airPages } from '@airlib/vite';

export default defineConfig({
  plugins: [
    airPages({
      noscript: true, // Ships pure static HTML/CSS with 0KB client JavaScript site-wide
    }),
  ],
});
```

When rendered, static pages are emitted as dehydrated HTML files with `<script>` tags completely stripped, achieving instant First Contentful Paint (FCP) and 100/100 Lighthouse performance.

## Extended Markdown & Content Authoring

### TanStack MDX Workflow

In TanStack, Markdown and MDX require configuring external bundler loaders, remark/rehype plugins, and manual component wrapping.

### AirLib Extended MDX

AirLib includes built-in, zero-config Extended Markdown (`.page.mdx`). You simply create `.page.mdx` files inside `pages/`:

- **Frontmatter as Route Metadata** — YAML frontmatter automatically integrates with the route tree, navigation sidebar, and document `<Head>`.
- **Built-in Admonitions** — Native support for `:::note`, `:::tip`, `:::warning`, `:::danger`, and `:::details`.
- **Tabbed Code Groups** — Native `:::code-group` blocks for multi-language and multi-package manager examples.
- **Embedded JSX** — Embed live, interactive React or SolidJS components directly inside markdown without boilerplate wrapper files.

## Performance & Reactivity Footprint

### Deferred Hydration & Instant FCP

In traditional frameworks, client-side hydration scripts execute immediately when JavaScript chunks load, competing with the browser's main-thread rendering and layout passes.

In AirLib, **SSR always delivers 100% complete, fully styled HTML**. Because the user already sees the full visual state, AirLib **defers client hydration by default** (customizable per-route via `deferred`). This gives the browser time to paint the page instantly without main-thread jank, delivering instant First Contentful Paint (FCP) and near-zero Total Blocking Time (TBT).

| Performance Vector | TanStack (Router + Query) | AirLib |
|---|---|---|
| **First Contentful Paint (FCP)** | Hydration scripts compete with initial render | Instant FCP (Complete SSR HTML + deferred hydration) |
| **Hydration Strategy** | Immediate synchronous client hydration | Non-blocking deferred hydration (configurable via `deferred`) |
| **Reactivity Model** | Virtual DOM reconciliation & query key cache checks | Fine-grained proxy mutations updating only touched DOM nodes |
| **Data Fetching Overhead** | Independent HTTP requests per query | Automatic tick-based IRPC request batching & streaming |
| **Static Bundle Size** | Full React runtime + Query engine on all routes | 0KB JavaScript static delivery option (`noscript`) |
| **Server Cold Starts** | Custom Node.js setup | Lightweight universal worker runnable across Bun, Node, Deno, & Edge |

## Multi-Runtime Deployment

TanStack Router is runtime-agnostic on the client, but SSR requires custom server plumbing for each deployment target.

AirLib builds a single **Universal SSR Worker** (`createApp`) that deploys identically across all major JavaScript runtimes with zero adapter overhead:

- **Bun** — `Bun.serve({ fetch: worker.fetch, websocket: worker.websocket })`
- **Node.js** — Native Hono/Node adapter
- **Deno** — `Deno.serve((req) => worker.fetch(req))`
- **Cloudflare Workers** — `export default { fetch: (req, env) => worker.fetch(req, env) }`

## Architectural Summary

| Dimension | TanStack (Router + Query) | AirLib |
|---|---|---|
| **Routing** | Code/file-based routing with CLI codegen | Assisted file-based routing |
| **State & Reactivity** | Immutable VDOM re-renders & Query Cache | Fine-grained reactive state |
| **Remote Functions** | Manual fetchers & query key invalidation | Isomorphic remote functions & streams |
| **Component Model** | Route module boundaries | Universal components |
| **Form Handling** | useMutation & manual status hooks | Direct reactive form state |
| **State Mutation** | Manual cache snapshots & rollback handlers | Direct reversible state mutations |
| **Hydration & FCP** | Immediate hydration competing with paint | Instant FCP & deferred hydration |
| **Static Generation** | SPA static build or custom SSR | Granular SSG & on-demand ISG |

| **Static JS Footprint** | Ships full React runtime | Zero-JavaScript static delivery option |
| **SSR Engine** | Custom server integrations | Zero-adapter universal SSR worker |

## Final thoughts

TanStack and AirLib approach full-stack React from different engineering philosophies:

**Choose TanStack if:** You prefer assembling your stack from modular, headless utilities. If you are building around existing REST or GraphQL APIs and need granular control over cache lifetimes and query keys, TanStack Query is unmatched.

**Choose AirLib if:** You prefer a unified ecosystem where routing, data fetching, and state management share the exact same reactive engine and type-safe function calls. With assisted file-based routing, zero-JS static publishing, built-in MDX authoring, and native zero-adapter deployment across Bun, Node.js, Deno, and Cloudflare, AirLib delivers a cohesive full-stack developer experience.
